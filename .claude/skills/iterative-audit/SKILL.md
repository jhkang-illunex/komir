# Iterative Audit — 다중 에이전트 감사→수정→배포→재검사 루프

여러 개의 독립된 피어 세션(이 프로젝트에서는 `git worktree` 기반 병렬 에이전트,
예: streamlit-agent·report-summary-agent·chatbot-agent)에게 각자 담당 영역을 감사시키고,
그 결과를 오케스트레이터(이 스킬을 실행하는 세션 = "main-agent")가 취합해 수정을
지시 → 각 에이전트가 자기 워크트리에 커밋 → main-agent가 main에 머지하고 재배포 →
재검사를 지시 → 수렴할 때까지(또는 라운드 상한까지) 반복하는 워크플로다.

핵심 문제의식: 감사 결과를 그냥 문서로 남기고 끝내는 게 아니라, "고쳐졌는지까지
확인"하는 루프를 코드 수정 없이 조율만으로 안전하게 반복시키는 것. 오케스트레이터
자신은 원칙적으로 코드를 직접 고치지 않는다 — 지시하고, 병합하고, 배포하고, 검증한다.

## 최우선 원칙 — 감사도 수정도 항상 근거 자료 기반

이 루프 전체를 관통하는 최우선 규율이다: **추측으로 판정하거나 "고쳤다"고 주장만 하는
것을 절대 허용하지 않는다.**

- **감사 단계**: 발견은 재현된 캡처(스크린샷, 실제 요청·응답 원문, `docker exec`로
  확인한 내부 상태, 코드 라인 인용)로 뒷받침한다. 코드를 읽고 "이럴 것 같다"로 끝내지
  말고 실제로 실행해서 확인한다.
- **수정 지시 단계**: 감사에서 이미 확보한 근거를 그대로 인용해 지시한다(에이전트가
  원인을 처음부터 다시 추측하게 하지 말 것). 근본 원인이 불확실하면 "먼저 재현해서
  원인을 확정한 뒤 수정"을 지시에 명시한다.
- **수정 완료 보고 단계**: 수정 전/후를 **같은 조건으로 재실행해 대조한 근거**를 반드시
  포함하게 한다 — "고쳤습니다"만 있고 재현 캡처가 없는 보고는 완료로 인정하지 않는다.
- **재검사 단계**: 오케스트레이터도 "머지·배포했으니 됐다"고 넘어가지 말고, 실제 배포된
  환경(§착수 전 필수 확인 #3에서 확인한 그 프로세스/컨테이너)에 대해 재검사를 시켜 근거를
  받는다.

라운드 지시를 작성할 때마다 이 원칙을 한 줄이라도 명시적으로 포함할 것 — 한 번
안내했다고 다음 라운드에서 생략하지 않는다(에이전트가 여러 라운드를 거치며 "이번엔
급하니 근거 없이 진행"으로 흐르기 쉽다).

## 언제 쓰는가

- 사용자가 여러 화면/서비스에 대해 "감사해줘", "점검해줘"를 여러 피어 세션에 병렬로
  맡기고 싶어할 때(먼저 `ListAgents`로 대상 세션 확인).
- 감사 결과가 나온 뒤 "이거 고쳐질 때까지 루프 돌려줘", "수정→재배포→재검사 반복해줘"
  같은 지시가 나올 때.
- 참여 세션들이 **서로 다른 git worktree**에서 독립적으로 커밋 가능한 구조일 때(코드
  수정이 실제로 파일시스템 레벨에서 격리돼 있어야 병렬 수정이 안전함).

**아닌 경우**: 일회성 리뷰는 `/code-review`나 `skeptic-code`. 에이전트가 하나뿐이면
그냥 직접 지시하면 되고 이 루프의 오케스트레이션 오버헤드가 필요 없다.

## 착수 전 필수 확인 (건너뛰면 라운드가 통째로 무의미해짐)

1. **`ListAgents`로 참여 세션과 idle 상태 확인.** 이름이 곧 주소 — `SendMessage`의
   `to`에 `"이름 [ref]"` 그대로 사용.
2. **워크트리 동기화 상태.** 각 피어 세션이 어떤 워크트리(`git worktree list`)에서
   도는지, 그 워크트리의 HEAD가 main 대비 몇 커밋 뒤처졌는지 `git merge-base
   --is-ancestor <worktree-HEAD> <main-HEAD>` + `git rev-list --count`로 확인. 뒤처진
   워크트리에는 **작업 지시에 "먼저 `git merge main`부터"를 명시적으로 포함**할 것 —
   안 하면 머지 시 충돌하거나 구코드 기준으로 수정하게 됨.
3. **실제 배포가 어디서 소스되는지 실측.** "머지하면 반영된다"는 가정을 검증 없이
   믿지 말 것.
   - 상시 실행 프로세스(예: streamlit): `ls -l /proc/<pid>/cwd`로 실제 참조 경로가
     main 체크아웃인지 워크트리인지 확인.
   - 컨테이너: `docker inspect <container> --format '{{.Config.Image}}'`로 이미지
     태그·빌드 시각 확인 — main 머지 후 반드시 재빌드해야 재검사가 최신 코드를 본다.
   - **캐시 인벤토리도 이 시점에 같이 만든다.** `grep -rn "st.cache\|lru_cache\|_cache\b"`
     등으로 대상 코드베이스의 프로세스 레벨 캐시를 미리 찾아 목록화(어떤 함수가
     캐시되는지, TTL이 있는지, 재시작으로 비워지는지, reload 엔드포인트가 있는지) —
     라운드마다 이 목록대로 클리어한다(아래 4번 절차 참고).
4. **파일 소유권을 라운드 시작 전에 명시적으로 분배.** "누가 그 문제를 발견했는가"가
   아니라 "그 파일을 누가 담당하는가"로 수정 담당을 정한다. 한 파일을 여러 에이전트가
   동시에 건드리게 하지 말 것 — 이 프로젝트에서 실제로 워크트리 divergence 사고가
   있었다(`chatbot_rule_tone_type_260828` 메모리 참고: 같은 파일을 두 세션이 각자
   포크 시점 기준으로 손대 병합 시 충돌·재작업 발생). 감사자가 다른 파일 소관의
   버그를 발견했다면, 그 항목은 파일을 담당하는 에이전트에게 **이관**한다.
5. **제외 목록을 먼저 확정한다.** 구조적으로 이번 루프 범위 밖인 항목(계산 로직 신규
   개발이 필요한 갭, 아키텍처 한계, 사용자가 이미 유지/보류로 결정한 항목, 공개 API
   계약 변경이 필요한 항목 등)을 라운드1 시작 전에 목록화해두지 않으면, 매 라운드
   같은 "고칠 수 없는" 항목이 재보고되며 루프가 절대 수렴하지 않는다.

## 역할 분담 (라운드 내내 고정)

- **각 피어 에이전트**: 자기 워크트리 안에서만 감사·수정·커밋. 공유 인프라(도커
  컨테이너 재기동, 공유 DB에 대한 비가역 조작 등)는 직접 건드리지 않는다 — 다른
  세션과 경합하면 감사 재현성이 깨진다(실제로 감사 도중 다른 세션이 컨테이너를
  재기동해 재현 실패한 사례가 있었음).
- **main-agent(오케스트레이터, 이 스킬을 실행하는 세션)**: 지시 작성·git merge to
  main·재빌드/재기동·배포 검증·재검사 지시. **git merge와 배포는 오케스트레이터만
  수행**한다.

## 라운드 절차

1. **감사 지시**(라운드1에만 해당, 2라운드부터는 "재검사 지시"로 대체): 대상별로
   나눠 병렬 발송. 각 지시에 명시할 것 — (a) 조사만 하고 코드는 고치지 말 것, (b)
   산출물 저장 경로(예: `documents/산출물/<주차>/`), (c) 세션 리밋 걸리면 대기 후
   재개할 것, (d) 완료 시 main-agent에게 SendMessage로 보고.
2. **취합·재배정**: 여러 에이전트의 감사 결과에서 겹치는 파일 소유권 충돌을 먼저
   정리(위 "착수 전 필수 확인" #4). 우선순위(P0/P1/P2 등)를 매기고 제외 목록과
   대조해 이번 라운드에서 실제로 지시할 항목만 추린다.
3. **수정 지시**: 에이전트별로 "당신 전담 파일" 범위를 명시하고, 구체적 파일·라인·
   원인·처방까지 적어 보낸다(에이전트가 스스로 원인 분석부터 다시 하게 하지 말 것 —
   감사에서 이미 나온 근거를 그대로 인용). 계약/아키텍처를 바꿔야 근본 해결되는
   항목은 "범위를 한정한 임시 처방 + 다음 라운드/사용자 논의 항목으로 기록"까지
   명확히 지정해 에이전트가 임의로 API 계약을 바꾸지 않게 한다.
4. **커밋 대기**: 에이전트가 자기 워크트리에 커밋 후 보고할 때까지 기다린다(cross-
   session 메시지가 도착하면 자동으로 다음 턴에 전달됨 — 폴링하지 말 것).
5. **머지**: `git merge <worktree-branch>`를 main 체크아웃에서 실행. 충돌 시 임의로
   한쪽을 버리지 말고 실제 diff를 확인.
6. **재배포 + 검증 + 캐시 클리어**: 영향받은 프로세스/컨테이너를 재빌드·재시작하고,
   위 "실제 배포가 어디서 소스되는지" 재확인 절차를 반복해 최신 코드가 실제로 떠
   있는지 확인한 뒤에만 다음 단계로 진행. **라운드마다 캐시를 반드시 클리어한다** —
   재기동 없이 파일만 바뀌면 코드 자체는 반영돼도 프로세스 내부 캐시(`@st.cache_data`/
   `@st.cache_resource`/`lru_cache`/모듈 전역 dict 캐시 등)가 이전 라운드 데이터를
   들고 있어 재검사가 "고쳤는데 그대로"라는 거짓 신호를 낼 수 있다. 착수 전 확인
   단계에서 캐시 종류를 인벤토리해두고(각 캐시가 프로세스 재시작으로 비워지는지,
   TTL이 있는지, 별도 reload 엔드포인트가 필요한지), 라운드마다 그 목록 그대로
   비운다 — 가장 확실한 방법은 프로세스/컨테이너 자체를 재시작하는 것(TTL 만료를
   기다리지 않는다).
7. **재검사 지시**: 전체 감사를 처음부터 다시 시키지 말고, **이번 라운드에서 고친
   항목의 검증 + 그 파일 주변의 타겟 회귀**만 시킨다(전체 재스윕은 라운드 수가
   늘수록 비용이 기하급수적으로 늘어 5라운드 안에 안 끝난다).
8. **상태 파일 갱신**: 아래 템플릿의 라운드 트래커에 이번 라운드 결과(무엇을
   고쳤는지, 무엇이 남았는지, 신규 발견이 있는지)를 기록.
9. **종료 판정**: 제외 목록 밖에서 신규 P0/P1이 없으면 루프 종료. 아니면 다음
   라운드로(최대 라운드 수는 기본 5, 사용자가 다르게 지정했으면 그 값).

## 세션 리밋 대응

- 모든 지시 메시지 끝에 "세션 리밋 걸리면 풀릴 때까지 기다렸다가 이어서 진행해줘"를
  명시적으로 포함한다 — 피어 세션은 이 지시가 없으면 리밋에 걸렸을 때 그냥 멈춘 채로
  남을 수 있다.
- **잔여 사용량이 애매할 때도 "일단 대기"를 명시적 선택지로 제시한다.** 리밋에
  걸렸는지 안 걸렸는지 불확실한 상황(예: 경고성 신호만 있고 확정 차단은 아닌 경우)에서
  에이전트가 무리하게 계속 진행하거나 반대로 임의로 작업을 포기하지 않도록,
  "애매하면 무리해서 진행하지 말고 그냥 대기했다가 확실해지면 이어가도 된다"를
  지시에 포함한다 — 애매한 상태에서 무리하게 밀어붙이다 근거 없는 결과를 내는 것보다
  낫다.
- 오케스트레이터 자신도 컨텍스트 압축·세션 중단을 겪을 수 있으므로, 진행 상태를
  **대화 맥락이 아니라 파일**에 남긴다(아래 템플릿). 파일이 있으면 세션이 재개되거나
  압축된 뒤에도 어느 라운드까지 왔는지, 무엇이 남았는지 즉시 복구 가능하다.
- cross-session 메시지는 도착하면 자동으로 다음 턴에 전달된다 — "아직 응답 왔나"를
  확인하려고 `ListAgents`를 반복 호출하거나 짧은 간격으로 대기하지 말 것.

## 라운드 트래커 템플릿

`documents/산출물/<주차>/<주제>_감사_수정루프_상태.md` (이 프로젝트 컨벤션 기준
경로 — 다른 프로젝트라면 그 프로젝트의 산출물 경로를 따를 것)에 아래 골격으로 작성:

```markdown
# <주제> 감사→수정→재검증 루프 상태

## 개요
- 참여: <에이전트별 담당 영역>
- 루프: 커밋 → 지시 → 수정·커밋 → 머지 → 배포 → 재검사 → 반복
- 종료 조건: (a) 제외목록 밖 신규 P0/P1 없음, (b) 라운드 <N>회 도달
- 파일 소유권: <에이전트>: <경로 glob> (라운드 내내 고정, 위반 시 재배정)
- 배포 소유권: git merge·재기동은 main-agent만
- 배포 실측: <프로세스/컨테이너별 소스 확인 결과, 라운드마다 갱신>

## 제외 목록(구조적으로 범위 밖 — 재보고 불필요)
- <항목> — <이유>

## 라운드 N
### <에이전트> 지시 내용(파일: <glob>)
1. [Pn] ...
### 진행 상태
- [ ] <에이전트> 수정 완료·커밋
- [ ] main-agent: main 머지
- [ ] main-agent: 재배포 확인
- [ ] main-agent: 재검사 지시
- [ ] 재검사 결과: <신규 P0/P1 유무>
```

## 자주 하는 실수 (실제로 겪은 것)

- **감사자 == 수정자로 잘못 배정.** 감사한 에이전트가 아니라 그 파일을 담당하는
  에이전트에게 수정을 지시해야 한다. 감사 리포트를 그대로 옮겨 지시하면 이 실수를
  하기 쉬우니, 지시 작성 직전에 파일 경로 기준으로 다시 분류할 것.
- **워크트리 동기화 생략.** 뒤처진 워크트리에서 바로 수정→커밋하면 머지 충돌이나
  구코드 기준 수정이 나온다.
- **배포가 실제로 최신 코드를 서빙하는지 검증 안 함.** 머지했다고 재검사 결과가
  유효해지는 게 아니다 — 프로세스 cwd·컨테이너 이미지 빌드 시각을 확인.
- **종료 조건 없이 시작.** 구조적으로 못 고치는 항목(신규 기능 필요, 아키텍처 한계,
  사용자 보류 결정)을 제외 목록으로 미리 못 박지 않으면 루프가 절대 안 끝난다.
- **매 라운드 전체 재감사.** 비용이 라운드마다 누적돼 상한 안에 못 끝난다 — 고친
  항목 검증 + 근접 회귀만.
- **공유 인프라를 에이전트가 직접 건드리게 둠.** 도커 재기동 등은 오케스트레이터만.
- **근거 없는 "완료" 보고를 그대로 수용.** 수정 전/후 대조 캡처가 없는 보고는 완료로
  치지 말고 재현 근거를 요청할 것 — 특히 라운드가 반복될수록 이 규율이 느슨해지기 쉽다.
- **캐시를 안 비우고 재검사.** 재빌드했더라도 TTL 캐시(`st.cache_data` 등)가 만료
  전이면 재검사가 이전 라운드 데이터를 보고 "그대로"라고 오판할 수 있다 — 프로세스
  재시작으로 확실히 비울 것.
