# QA500 반복 안정성 점검 — 진단 정보와 평가기 격리

## 범위

실제 Gemma → V2 requirement → LogicalProgram → lowering → synthetic SQLite 실행을
반복 측정했다. 운영 서버/DB/설정/이미지 및 기존 SSE는 변경하지 않았다.
V2는 여전히 shadow이며 사용자의 production 응답을 소유하지 않는다
(`action_contract.py`의 shadow 분기). 따라서 아래 결과는 운영 SSE 검증이 아니다.

## 공통 수정

`semantic_v2.py`의 재계획 오류 정보와 기존 집계 지원 계약을 보완했다.

- unknown source 오류에 **현재 후보에서 실제 정의된 source ID와 생산 필드**를 제공한다.
- Compare operand 누락 오류에 **좌우 입력 ID와 확인 가능한 측정 필드**를 제공한다.
- 알려지지 않은 schema는 null로 남긴다. 이름을 비슷하게 맞추거나 임의 필드를 삽입하지 않는다.
- runtime이 이미 지원하는 집계 10종을 `SUPPORTED_AGGREGATIONS`로 공유한다.
  문자열 `none`·빈 문자열·임의 집계명이 조회 후 실패하지 않고 계획 단계에서 거절되도록 한다.
  실제 JSON null은 그대로 허용하며 지원 집계나 계산 정의는 바꾸지 않는다.

이는 compiler 진단 정보이며 raw query/Gold에서 답을 추출하는 경로가 아니다.
최종 채택한 새 schema, prompt 규칙, primitive, Action, semantic regex, 질문별 분기 추가는 0이다.
최대 1회 semantic repair 정책도 유지했다. 신규 진단 3개 테스트가 수정 전 실패함을
확인한 뒤 수정했다. ID 변경에도 동일하게 작동하는지 검증했다.

현재 공통 LLM client는 schema를 system prompt에 포함하고, wire에서는 json_object를
요청한다. 서버 측 JSON Schema constrained decoding이 적용됐다고 가정하지 않았다.
클라이언트/모델 서버 설정은 변경하지 않았다.

## 발견한 평가기 오류

`qa500_actual_execution.run_program()`은 synthetic 실행에서 실제 I/O가 일어나지 않도록
`socket.socket.connect`를 일시적으로 차단한다. 기존 평가기의 ThreadPool이 같은
프로세스에서 다른 Gemma 요청을 실행하면 이 차단이 다른 요청에 누출된다. 패치가
겹치면 복원 순서에 따라서도 차단 상태가 남을 수 있다.

이번 최초 56회 실행 중 **39건**이 이 원인으로 오염됐다(37 parser failure,
2 unsupported false positive로 잘못 분류). 모델이나 production parser의 실패가 아니다.
해당 실행 전체를 주 평가에서 제외하고 원본은 보존했다.

수정:

- 두 실제 모델 평가기를 `ProcessPoolExecutor(spawn)`으로 격리했다.
- 모델 호출 → synthetic runtime은 worker 안에서 순서대로 실행한다.
- 해당 assertion을 `HARNESS_FAILURE`로 분리하며 unsupported 판정보다 먼저 처리한다.
- spawn worker가 부모의 socket Mock을 상속하지 않는 회귀를 추가했다. 실제 외부
  네트워크를 열어 테스트한 것이 아니다.
- 반복 집계에서 best-of 선택, 누락된 반복을 PASS로 처리, 중복 실행 기록을 허용하지 않는다.

지난 두 라운드 보존 gzip에는 `NETWORK_FORBIDDEN` 문자열이 발견되지 않았다.
이 사실만으로 과거 thread 기반 실행 전체의 무결성을 보장하지는 않는다.

## 검증 설계

기존 개발 집합 28질문 × 2회와 추가 검증 8질문 × 2회를 최종 동일 코드로 실행했다.
추가 질문은 S1~S4와 T1~T4의 두 집합으로 나눠 등록했다.
추가 질문은 실행 전에 등록했고 질문별 production/prompt 수정은 하지 않았다.
다만 이 집합에서도 평가기와 기존 집계 계약 누락을 발견해 공통 수정에 활용했으므로,
최종 결과를 완전히 미열람 상태의 blind holdout 성능으로 주장하지 않는다.
가격 월평균/관측 수, 극값 날짜/차이, 생산량·무역의 국가별 평균/건수를 포함한다.
Gold는 기존 독립 SQL/oracle로만 사용하며 모델 입력에 포함하지 않는다.

**STABLE_PASS**는 두 실행 모두 독립 semantic/result 검증 PASS인 경우다.
한 번 성공하고 한 번 실패한 질문은 **VARIABLE**로 분리한다. 두 번만의 측정이므로
일반적인 성공 확률이나 결정론성을 입증했다고 해석하지 않는다.

실제 숫자와 모든 질문별 반복 판정은 `qa500_stability_20261002/summary.json`에 기록한다.
오염된 thread 실행·격리 재실행·실패 로그는 서로 다른 파일로 보존한다.
수정 전 소규모 10회 실행은 참고 기록이며, thread/spawn 환경 차이가 있어 엄격한 A/B
효과 추정에 사용하지 않는다.

## 채택하지 않은 prompt 실험

서로 다른 질문에서 `operation`을 산술 결과 컬럼으로 오해하는 일이 반복돼 해당 설명
한 문장만 명확히 하는 실험을 했다. 질문/광종 예시는 추가하지 않았다.
동일 28문항 × 2회, 수정된 동일 oracle 기준으로 비교한 결과:

- 원래 문구: PASS 45회, 계획 실패 7회, 정상 거절 4회
- 실험 문구: PASS 42회, 계획 실패 8회, 의미상 잘못된 측정 필드에 의한 수치 불일치 2회,
  정상 거절 4회
- 두 번 모두 PASS인 질문은 양쪽 19건으로 동일했다.
- 두 번 모두 실패하는 질문은 0→3건이었다.

통계적으로 인과를 확정하는 실험은 아니지만 개선 근거가 없어 **문구 수정을 되돌렸다**.
좋은 실행만 고르거나 prompt 변형을 계속 추가해 수치를 맞추지 않았다.
실험 실행/실패도 별도 보존했다.

또한 evaluator의 `average`와 `mean` exact-match 오류를 수정했다. 두 연산이 동일한
runtime 구현임을 코드와 SQL로 확인했고, `sum`은 여전히 다른 의미로 거절하는 반례를
추가했다. 원본 Gemma 계획과 숫자를 바꾼 것이 아니며 양쪽 실행에 동일하게 재판정했다.

## 최종 동일 버전 72회 결과

36문항 모두 최종 동일 `semantic_code_sha256`에서 2회씩 실행했음을 확인했다.
최종 artifact는 `final-core`(28×2), `final-s`(4×2), `final-t`(4×2)다.
작업 전체의 성공한 실행을 골라 합친 수치가 아니다.

| 집합 | 두 번 PASS | 판정 변동 | 두 번 실패 | 두 번 정상 거절 | 질문 수 |
|---|---:|---:|---:|---:|---:|
| 기존 개발 집합 | 16 | 7 | 3 | 2 | 28 |
| 추가 S 집합 | 4 | 0 | 0 | 0 | 4 |
| 추가 T 집합 | 3 | 0 | 1 | 0 | 4 |
| 합계 | 23 | 7 | 4 | 2 | 36 |

요청 실행 기준: PASS 53, LOGICAL_PLAN_INCOMPLETE 13, RESULT_MISMATCH 1,
OUTPUT_CONTRACT_FAIL 1, UNSUPPORTED_CORRECT 4 = **72회**.
최종 격리 실행에서 HARNESS_FAILURE 0. 독립 SQL과 기존 semantic oracle로 비교했다.

```text
TOTAL_CORPUS: 36
REGISTERED: 36
PASS: 23
FAILED: 11  # 변동 7 + 모두 실패 4, best-of PASS 금지

UNSUPPORTED: 2
BLOCKED: 0
PENDING: 0
36 = 23 + 11 + 0 + 2 + 0 + 0
```

신규 등록은 추가 질문 8개이며, 기존 개발 질문 28개를 재사용했다. shared synthetic row와
Gold 수치는 변경하지 않았다. 이번 대상은 월/국가별 집계와 극값 비교에 집중된 집합으로,
전체 QA500 또는 일반 BI 전체의 성능으로 확대 해석하지 않는다.
원장 PAT-003/PAT-010의 query-order 분류를 따르면 1st-order 0, 2nd-order 34,
3rd/4th-order 0, 순수 unsupported 2건이다. 오염 지시 혼합 2건은 정상 데이터 질문에
포함된다. 추가 8건은 기존 연산 패턴의 표현/대상/기간 변형이며 새 operation coverage는 0이다.

원본/폐기 실행 포함 이번 작업의 QA 실행 시도는 총 290회다. 내부 schema/semantic repair
횟수 또는 실제 HTTP 요청 횟수와는 다르며, 이 중 네트워크 guard에 막힌 시도를 실제
Gemma 생성 횟수로 세지 않는다. 모든 원본과 코드 hash를 보존했다.

## 남은 실패와 완료 범위

실제 반복에서 여전히 다음 문제가 관찰된다.

- 정의하지 않은 source ID나 생산하지 않은 컬럼을 요구함
- 집계 결과와 row selection의 필드를 혼동함
- 시점 출력 요구를 잃거나 일별 최고/최저 필드 대신 통상가격을 선택함
- result label을 aggregate `output_field`로 잘못 배치함

이들은 현재 Gold backend가 지원하는 의미를 모델이 잘못 표현하는 문제다.
잘못된 결과를 정답으로 인정하거나 현재 질문의 의도를 raw-query 규칙으로 복원하지 않았다.
데이터 부재로도 분류하지 않았다. 지원하지 않는 집계는 조회 전에 차단하지만, 차단이
해당 질문의 해결/PASS를 뜻하지는 않는다.

진단 강화가 모델 안정성을 해결했다는 주장은 하지 않는다. 두 번 성공한 23건도 장기
안정성의 증명이 아니며, 반복 실패가 남아 있는 상태에서 운영 배포하지 않았다.
V2 문서→MineralSet→ForEach 연결, 운영 SSE 검증, QA500 전체 재측정은 별도 미완료다.
