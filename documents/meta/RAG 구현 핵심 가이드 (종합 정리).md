# RAG 구현 핵심 가이드

지금까지 정리한 RAG / GraphRAG / 온톨로지 관련 노트 약 40건 중에서, **실제 구현에 쓸 수 있는 조언만** 추렸습니다. RAG 역사, 트렌드 서술, "RAG는 죽었다"류 수사적 주장, 개인 프로젝트 세부사항은 제외했습니다.

> **한 줄 요약**: RAG 실패의 대부분은 검색 알고리즘이 아니라 (1) 아키텍처를 질문 유형에 안 맞게 고른 것, (2) 문서 거버넌스·스키마 부재, (3) "모르면 모른다고 말하기"를 시스템에 강제하지 않은 것에서 온다.

---

## 1. 아키텍처 선택 기준 — 무엇을 언제 쓸까

기술을 먼저 고르지 말고, **실패 유형**을 먼저 진단하는 것이 가장 실무적인 접근입니다.

| 증상 | 원인 | 해법 |
|---|---|---|
| 답이 한 문단 안에 있는데도 가끔 틀림 | 검색/생성 문제 | 바닐라 RAG (과설계 금지) |
| 답이 긴 문서 하나 안에 있는데 검색이 엉뚱한 섹션에 착지 | 탐색(navigation) 문제 | PageIndex류 — 단, 문서에 실제 목차·위계 구조가 있을 때만 작동 |
| 문서를 가로질러 연결·카운팅하거나 "지금 참인 것"을 알아야 함 | 구조(structure) 문제 | GraphRAG — 부재(absence) 질문, 시간에 따라 바뀌는 사실에 강함 |
| 뉘앙스와 구조가 둘 다 필요 | 복합 | 하이브리드 + 질문 유형별 라우팅 |
| 답이 구조화 데이터로부터 계산 가능 (매출, 통계 등) |애초에 RAG 문제가 아님 | SQL/Cypher 생성·실행이 텍스트 청크 검색보다 거의 항상 낫다 — **구조화 데이터는 임베딩하지 말 것** |
| 코드베이스, 사설 저장소 | grep/glob으로 충분 | Agent-as-Retriever (벡터 인덱스 없이 필요할 때 로드) — 단, 페타바이트급 코퍼스나 진짜 시맨틱 검색(동의어 분산)엔 약함 |

추가 판단 질문 3가지 (RAG를 아예 안 써도 되는 경우 걸러내기):
1. 인덱싱된 관계형 DB로 풀 수 있는 문제인가?
2. 데이터가 지속적 임베딩 갱신을 정당화할 만큼 자주 바뀌는가?
3. 이건 검색 문제인가, 데이터 품질 문제인가? (후자면 RAG를 아무리 고도화해도 안 고쳐짐)

**주의**: "복잡도를 더한다고 품질이 오르지 않는다." GraphRAG·에이전틱 검색 같은 고급 패턴은 그것이 다루는 특정 실패 모드가 실제로 존재할 때만 도입합니다.

## 2. 검색 전략

- **기본 조합**: 하이브리드 검색(BM25 + dense) → RRF(Reciprocal Rank Fusion)로 후보 통합 → 리랭킹. 여러 노트에서 반복 검증된 패턴(예: 후보 150개 → 20개로 압축).
- **넓이가 깊이보다 낫다**: top-k를 무작정 키우기보다, 실패 모드가 서로 다른 리트리버를 추가하는 편이 효과적입니다 (dense+BM25, 문서+표, 벡터+그래프). 리트리버 품질이 어느 수준을 넘으면 top-k 확장의 효과는 급격히 줄어듭니다(중복 청크, long-context "lost in the middle").
- **질의 라우팅**: 질문을 no_retrieval / single-hop / multi-hop으로 분류해 필요한 곳에만 연산을 씁니다. 잘못된 전제(false-premise)를 미리 걸러내는 탐지기는 하드 게이트가 아니라 보조 신호로만 쓰는 것이 안전합니다(오탐이 많음).
- **ColBERT / Late Interaction**: 문서·질의를 단일 벡터로 뭉개지 않고 토큰 단위 매칭을 유지해 정확도를 높이는 방식. 저장·연산 비용이 늘어나는 대신 법률·금융처럼 근거가 문서 전반에 흩어져 있고 정확도가 중요한 도메인에 적합합니다. 실전 패턴은 "싼 1차 후보(BM25/단일벡터) → late interaction으로 정밀 재정렬".
- **구조화 데이터는 임베딩하지 말 것** (위 표와 동일 원칙): 계산 가능한 답은 SQL/Cypher 생성이 텍스트 검색보다 거의 항상 정확합니다.
- **에이전틱 검색(다단계 재작성·재검색 루프)**: 모호하고 다단계인 질문에 강하지만, 여러 출처에 걸친 넓은 recall이 필요한 케이스(다수 문서를 얕게 훑어야 하는 유형)에는 오히려 약할 수 있습니다. 토큰 비용이 크므로 무조건 도입하지 말고, 실제로 다단계 추론이 필요한 질문 유형에만 씁니다.

## 3. 인덱싱·스키마 — 검색 전에 정리부터

- **스키마가 품질의 80%를 좌우한다.** 도메인 특화 스키마를 쓴 구현이 "자가조직화"를 표방한 스키마 없는 구현보다 모든 질문에서 정확했고, 후자는 실제로 며칠 만에 폐기된 사례가 있습니다.
- **스키마는 "역량 질문(competency questions)"에서 역으로 설계**합니다: (1) 실제 사용자가 물을 법한 질문 목록을 먼저 뽑고 → (2) 그 질문에 답하는 데 필요한 최소한의 클래스·관계만 정의 → (3) 실제 요구가 생길 때만 확장. "도메인에 대해 아는 모든 것"을 모델링하려다 거대하고 안 쓰이는 스키마가 되는 것이 흔한 실수입니다.
- **온톨로지·통제어휘는 새로 만들기보다 기존 표준에 정렬**시키는 편이 안전합니다 (예: 국가명은 Wikidata, 의학 용어는 MeSH). 처음부터 새 온톨로지를 만드는 경우는 드물어야 합니다.
- **그래프 위생(hygiene)은 팀들이 가장 과소평가하는 단계**입니다: 유사 엔티티 중복 제거·병합, 연결 안 된 고아 노드 제거, alias→canonical 통합. 이 작업 없이는 "추출 완료"이지 "검색 준비 완료"가 아닙니다.
- **소규모 배치로 점진 처리**: 한 번에 수십 건을 몰아넣지 말고 하나씩(또는 소량씩) 처리하면 문제가 생겼을 때 원인 추적이 훨씬 쉽습니다.

## 4. 환각을 줄이는 파이프라인 (효과 우선순위 순)

가장 이식성 높은 원칙: **"모델이 절대 틀리지 않게 만들려 하지 말고, 증명 가능한 것만 말하고 나머지는 기권(abstain)하게 하라."** 목표는 환각 0%가 아니라, 측정하고 튜닝 가능한 낮은 수치입니다.

1. **검증 게이트 + 보정된 기권 (가장 효과적)**: 답변을 개별 주장(atomic claims)으로 쪼갠 뒤 각 주장을 인용 근거와 대조하고, 하나라도 근거 미달이면 답변 전체를 기권으로 전환합니다. 이 방식이 걸린 대가(coverage 저하)와 얻는 것(환각률 급감)은 risk-coverage 곡선으로 운영 기준점을 정해야 합니다. 검증기(verifier)의 품질이 시스템 전체 성능의 실질적 상한선이므로, 여기에 투자하는 것이 가장 효율적인 개선 지점입니다.
2. **문장 단위 인용 강제**: 시스템 프롬프트로 외부지식 사용을 금지하고 문장마다 근거 인용을 강제하며, 생성 후 실제 청크와 매칭되지 않는 "날조 인용"은 사용자에게 도달하기 전에 제거합니다.
3. **검색 품질 자체를 높이는 것**: 노이즈 있는 검색은 환각을 거의 보장합니다. 하이브리드+리랭킹, 멀티홉 교차검증이 여기 해당합니다.
4. **구조화 지식으로 그라운딩**: 자연어 답변 생성 전에 Cypher/SQL 같은 정확한 쿼리로 데이터를 확정하는 방식이, 특히 숫자·통계 관련 환각에 강합니다.
5. **사후 사실검증 + 평가 루프**: Faithfulness, Groundedness, context recall 지표와 관련 벤치마크(아래 6장)로 지속 모니터링합니다.
6. **프롬프트 엔지니어링(보조 수단)**: "모르면 모른다고 말하라", CoT 등은 적용은 쉽지만 단독으로는 약하며 위 기법들의 보조 수단입니다.

추가로 알아둘 함정 두 가지:
- **"context poisoning"**: 벡터 검색이 의미상 가깝지만 실제로는 다른 범주의 문서를 가져와, 인용은 정확한데 근거 자체가 잘못된 범주인 환각이 생길 수 있습니다. 벡터로 1차 후보를 뽑은 뒤 온톨로지/그래프로 범주를 대조해 재랭크하는 방식이 완화책입니다.
- **불완전한 증거에서의 "그럴듯한" 오답**: 검색된 청크가 전부 실제로 존재하고 인용도 정확해도, 애초에 정답이 담긴 청크가 검색되지 않았다면(질문-정답 간 겹치는 단어가 없을 때 흔함) 그럴듯하지만 틀린 답이 나옵니다. 겉으로는 문제 없어 보이기 때문에 오히려 더 위험합니다.

## 5. 엔터프라이즈 RAG가 실패하는 진짜 이유

- **핵심 원칙: "RAG 패턴의 복잡도는 메타데이터 성숙도를 절대 넘어서면 안 된다."** 실패 원인은 대개 AI 모델의 한계가 아니라 정보 인프라 문제입니다: 문서 표준 불일치, 여러 버전이 여러 시스템에 흩어짐, "권위 있는 원본"이 지정되지 않음, 접근 제어 부재, 콘텐츠 신선도 관리 부재. 고급 RAG 패턴을 도입하기 전에 기본적인 문서 거버넌스부터 갖춰야 합니다.
- **접근 제어는 생성 후 필터링이 아니라 검색 시점에 강제**되어야 합니다. 권한 없는 사용자에게 데이터가 노출되는 사고는 "생성 후 걸러내면 된다"는 설계에서 나옵니다.
- **파이프라인 다이어그램에 안 나오는 것들이 실제 난이도의 대부분을 차지**합니다: PDF/이미지 파싱 같은 콘텐츠 처리, 청크 단위 접근 제어(ABAC), 컴플라이언스 요건, 실패 지점부터 재개 가능한 내구성 있는 오케스트레이션, 배포 전 사람의 개입 체크포인트, 페이지·버전·시점까지 포함한 출처 추적. 도입 전 점검 질문: 멀티모달을 지원하는가? 접근 제어가 실시간으로 강제되는가? 출력의 출처를 완전히 추적할 수 있는가? 실패 지점부터 재개 가능한가? 배포 전 사람이 검토하는 체크포인트가 있는가?
- **"AI 래퍼"(프롬프트+UI만 얹은 얕은 연동)의 한계**: 프롬프트 기반 안전장치는 행동을 "유도"할 뿐 "강제"하지 못합니다. 접근 제한, 응답 적절성 검증, 정보 유출 차단은 프롬프트만으로 안 됩니다. 명확한 정보 거버넌스 경로를 갖춘 내부 시스템 구조가 필요합니다.
- **참고**: "엔터프라이즈 RAG 72% 실패"류 수치는 원출처가 확인되지 않은 채 여러 블로그에서 반복 인용되는 패턴이 확인되었습니다. "AI 이니셔티브의 상당수가 PoC 이후 폐기된다"는 통계는 좀 더 신뢰할 만한 출처(S&P Global 등)가 있지만, 이는 AI 전반에 대한 조사이지 RAG 한정 통계는 아닙니다. 실패율 수치를 인용할 때는 원출처를 확인하는 것이 좋습니다.

## 6. 지식그래프(GraphRAG)를 붙일 때 유의점

- **KG의 실질 가치는 "정확도 향상"보다 "결과를 통제·설명할 수 있는 능력"**입니다. 정확도만 목표라면 다른 방법이 더 쌀 수 있습니다.
- **"벡터로 시작해서 필요할 때만 그래프를 얹어라."** 그래프 RAG는 대부분 로컬 1~3-hop 이웃 탐색만 필요하며, 전용 그래프 DB·그래프 쿼리 언어 없이 벡터 스토어 + 단순 순회(depth 1~3)만으로 충분한 경우가 많습니다.
- **아무 도메인에나 그래프RAG를 얹지 말 것**: 성공 사례들은 대개 "노드 개수가 조직·도메인 규모로 자연스럽게 제한되는" 좋은 유스케이스를 고른 결과입니다. 명확한 실패 모드(멀티홉 관계 질의, 관계 자체가 답인 질문) 없이 그래프 계층을 추가하면 복잡도만 늘고 성능은 오르지 않습니다.
- **파는 쪽이 잘 말하지 않는 GraphRAG 운영 비용 3가지**:
  1. 별칭(alias) 유지보수는 끝이 없습니다 — 엔티티 해소 실패는 순회 시작점 자체가 없는 조용한 버그로 이어집니다.
  2. 닫힌세계 답은 완전한 확신으로 틀립니다 — 추출 신뢰도가 완벽하지 않은 상태(대략 85% 수준)에서 관계 하나가 누락되면 권위 있어 보이는 오답이 나옵니다.
  3. "비어있음"이 "부재"를 의미하지 않습니다 — 쿼리 오류로 인한 빈 결과와 "정말 그런 사실이 없음"을 구분하는 로직을 직접 엔지니어링해야 합니다. 답변 프롬프트에는 "그런 사실 없음"이 아니라 "찾지 못함"이라고 말하도록 강제하는 것이 안전합니다.
- **GraphRAG와 온톨로지는 대체 관계가 아니라 보완 관계**입니다: GraphRAG(LLM 자동 추출, 빠르지만 규칙 강제가 약함) + 온톨로지(사람이 정의, 느리지만 동의어 매칭·모순 검출 가능)를 함께 쓰는 하이브리드가 대체로 더 안정적입니다. 온톨로지가 GraphRAG에 실제로 기여하는 지점은 질의 분해, 엔티티 해소 근거 제공, 검색 대상 필터링, disjoint 공리를 통한 답변 검증(타입 오류 탐지) 네 가지입니다.
- **자연어→SPARQL/Cypher 자동 생성은 아직 검증된 실전 사례가 드뭅니다.** 참고한 실전 튜토리얼 시리즈에서도 결국 모든 쿼리는 사람이 직접 짠 파라미터화 쿼리였습니다. "자동 생성"을 전제로 설계하지 말고, 사람이 검증한 쿼리 템플릿 + 파라미터 바인딩으로 시작하는 편이 안전합니다.
- **OWL(추론)과 SHACL(검증)은 역할이 다릅니다**: OWL은 오픈월드 가정이라 빠진 사실을 "거짓"으로 보지 않습니다(그래프가 불완전할 수 있음을 전제). 데이터를 실제로 거부·검증하려면 SHACL 제약이 필요합니다.

## 7. 평가 방법

- **골든 세트는 균형 있게 구성**: 답변 가능한 질문과 답변 불가능한 질문(전제가 잘못된 질문 포함)을 절반씩 넣어야, "시스템이 자신만만하게 없는 사실을 지어내는지"를 실제로 테스트할 수 있습니다.
- **주요 지표/벤치마크**: Faithfulness, Groundedness, context recall, TruthfulQA(모르면 보류하는 능력), HaluEval/HaluBench, Vectara HHEM. 다만 이런 지표들은 근거의 인과적 중요성까지는 알려주지 못합니다.
- **반사실(counterfactual) 평가로 보완**: 검색 결과를 없애거나(context ablation) 약한/무관한 근거로 바꿔서(counterfactual perturbation) 모델이 실제로 무너지는지 확인합니다. 근거를 빼도 답이 그대로면, 그 검색 스택은 실질적으로 장식(parametric memory에 의존)일 가능성이 높습니다.
- **문장 단위 귀속(retrieval attribution)**: 한 문단 안에 근거 있는 주장과 환각이 섞이면 전체 충실성 점수는 좋아 보일 수 있습니다. "이 청크가 답의 이 부분을 실제로 야기했는가"를 문장 단위로 평가해야 합니다. 규제 산업에서는 이것이 UI 부가 기능이 아니라 엔지니어링 요구사항입니다.
- **성능 수치를 인용할 때 주의**: 어떤 베이스라인 대비 개선인지, 평가지표가 다른 연구끼리 그대로 줄 세워 비교하고 있지는 않은지 확인이 필요합니다.

## 8. 규제/컴플라이언스 산업이라면 추가로 볼 것

일반 원칙에 더해 다음 5가지가 설계 초기부터 들어가야 합니다 (사후 추가는 시정 통보로 이어진 실제 사례가 있습니다):

1. **데이터 거주지·주권**: 리전 선택만으로는 부족하며, 실제 서비스 라우팅까지 문서로 검증해야 합니다.
2. **동의 관리**: 명시적·기한부 동의, 정해진 보존기간, 접근·삭제 권리. "삭제 권리"와 "감사 목적 장기 보존 의무" 사이의 긴장 관계를 설계 단계에서 미리 고려해야 합니다.
3. **불변 감사 아키텍처**: 조회 가능한 운영 로그와 변경 불가능한 장기 보존 로그를 이중으로 기록합니다. 개인정보는 안정적 해시 토큰으로 마스킹해 원본 노출 없이 세션 간 추적이 가능하게 합니다.
4. **주장 단위 설명가능성**: 개별 사실 하나하나(예: 요율, 시행일)를 원문 출처와 구체적 문구까지 연결합니다.
5. **규제 증거 패키징**: 인용이 달린 상호작용 이력, 품질 점수, 가드레일 판단을 자동으로 보고서화해 감사 대응 시간을 줄입니다.

추가로, 규제 산업에서는 **정확한 조항 매칭이 시맨틱 유사도만큼 중요**합니다 — 벡터 검색만으로는 부족하고, 시맨틱+키워드+구조화 쿼리를 함께 씁니다. 검색 경로를 설명해야 하는 요건이 있다면 PageIndex류(문서 목차를 따라가는 방식)가 유리할 수 있습니다.
