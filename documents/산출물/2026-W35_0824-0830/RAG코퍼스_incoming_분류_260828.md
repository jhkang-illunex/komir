### 1-1. ⚠ 재색인 4단계만으로는 안 지워지는 잔존 노출(승인 전 필수 확인)

프로덕션 컨테이너(`komir-rag-chat-test`)를 **읽기 전용**으로 확인한 결과(파일
열람·개수 세기만, 쓰기 0건):

```
$ docker exec komir-rag-chat-test find data_lake/semi_structure/okf_documents/산출물 -name '*.md' | wc -l
72
$ docker exec komir-rag-chat-test find data_lake/semi_structure/pageindex_trees -path '*산출물*' -name '*.json' | wc -l

```

`data_lake/semi_structure/okf_documents/산출물/`(W27~W33, 72개 md)와
`pageindex_trees/산출물/`(같은 수의 트리 json)이 이미 디스크에 존재한다. 그런데
`build_from_artifacts()`(OKF 생성)도 `build_pageindex_trees.build_all()`(트리
생성)도 **"현재 `load_documents()`가 반환하지 않는 파일은 지운다"는 로직이 없다**
— 둘 다 순수하게 "있으면 씀/건너뜀"만 하지, 소스에서 사라진 문서에 대응하는 기존
산출물을 **삭제(prune)하지 않는다**. `build_pgvector_index.py`(doc_chunk 갈래)만
매번 DELETE-후-재적재라 자동으로 동기화된다.

**결론**: 승인받은 4단계(`build_pgvector_index → build_okf_documents →
build_pageindex_trees → build_pgvector_okf`)를 새 `ROOT`(inhouse/incoming, 7건)로
그대로 실행해도, `doc_chunk.source_type='unstructured'`(갈래 A)에서는 71건이
정확히 빠지지만, **OKF 마크다운 72건 + PageIndex 트리 72건은 디스크에 그대로
남아 PageIndex 조회 경로로 계속 노출된다** — 오늘 이 작업의 목적(내부 문서
비노출)을 절반만 달성하게 된다. 이를 닫으려면 4단계 재색인과 별도로
`okf_documents/산출물/`·`pageindex_trees/산출물/` 두 서브트리를 **정리(전체
삭제 후 `build_from_artifacts`+`build_pageindex_trees`로 7건만 재생성, 또는
새 `load_documents()` 결과에 없는 파일만 선별 삭제)**하는 단계가 필요하다 —
이것도 production 마운트 볼륨에 대한 삭제 작업이라 **별도 승인 없이는 실행하지
않는다.** (OKF/트리는 원본 소스 문서에서 결정론적으로 재생성 가능한 파생물이라
Postgres `doc_chunk` 삭제 사고와 리스크 성격은 다르지만, 그래도 확인 후 진행을
권한다.)

**부수 발견 2(정보 공유용, 수정 안 함)**: `build_pgvector_index.py:73-77`의
`_src()`가 `week`에 `":"`가 없으면 무조건 `"documents/산출물"`을 `doc_chunk.src`
값으로 박아 넣는다. `inhouse/incoming/`은 평평한 구조라 `week`가 항상 `""`(§1의
week 버그 참고)이므로, 재색인 후에도 `src` 컬럼은 여전히 `"documents/산출물"`로
찍힌다 — 실제 소스 경로가 바뀌었는데 라벨은 안 바뀌는 것. 당장 기능에 영향은
없지만(그 값을 조건 분기에 쓰는 코드는 없어 보임, 표시용) 감사·추적 시 헷갈릴
수 있어 기록해 둔다. 고칠지는 판단이 필요하면 알려달라.

**부수 발견(정보 공유용, 이번 라운드에서 수정하지 않음)**: `load_documents()`의
`week` 필드 계산이 이미 깨져 있었다 — `ROOT`가 `documents/산출물`일 때
`os.path.relpath(full, ".")`(cwd=inhouse 기준 `../documents/산출물/<주차>/<파일>`)의
`parts[2]`를 week로 쓰는데, 실제로는 이 값이 항상 리터럴 문자열 `"산출물"`이었다
(주차 폴더명이 아님 — 실측 확인, 아래 §3). 챗봇 라이브 테스트 중 여러 번 관찰된
"(기준시점 산출물)"이라는 어색한 출처 표기가 이 버그의 실제 증상이었다. `ROOT`를
`inhouse/incoming/`(평평한 구조)으로 옮기면서 이 계산은 `week=""`(빈 문자열)로
바뀐다 — 틀린 상수보다 빈 값이 낫다고 판단해 **그대로 뒀다**(별도로 고치지 않음,
주석으로만 기록). `week` 로직 자체를 고치는 건 이번 작업 범위 밖이라 판단이
필요하면 알려달라.
