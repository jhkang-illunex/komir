# 프롬프트 관리 · 요약보고서 데모 UI/UX 감사 (2026-08-28)

## 0. 감사 개요

- **대상**: `inhouse/streamlit_demo` 멀티페이지 중 **프롬프트 관리**(`views/prompt_admin.py`)·
  **요약보고서 데모**(`views/report_demo.py`) 2개 화면.
- **범위**: 기능·UI/UX 점검 및 개선 우선순위 산정. **코드 수정 없음** — 전부 기록만 함(요청
  범위 준수).
- **방법**: 실행 중인 `streamlit run app.py`(:8501)와 `komir-report-gen-test` 컨테이너(:18003)를
  대상으로 Playwright(Chromium)로 실제 브라우저를 조작하며 조회·입력·제출·에러 유발까지
  직접 재현. 스크린샷은 `screenshots/`에 저장(상대경로로 본문에 링크).
- **비교 기준**: 같은 앱의 다른 화면(챗봇·데이터 관리·수급위기진단 stub)과 레이아웃·용어
  일관성을 대조.
- **환경 메모**: 샌드박스에 한글 폰트가 없어 최초 스크린샷이 전부 tofu(□)로 나왔다 —
  Noto Sans KR을 사용자 폰트 디렉토리에 설치해 해결(앱 자체 문제 아님, 감사 환경 이슈).
  또한 감사 중 `komir-report-gen-test` 컨테이너가 본 세션과 무관하게(다른 세션이 관리 중인
  것으로 추정) 재기동되는 것을 관측했다 — 프롬프트관리 화면의 "reload 실패" 케이스는 이
  경합 때문에 안정적으로 재현하지 못해 **코드 리뷰로 대체**했다(§4 참고, report_demo.py의
  동일 패턴은 실제로 재현·확인함).
- **DB 관련 주의**: 이 워크트리의 `.env`는 실제 공유 Postgres(`172.30.1.101:5433/komis_demo`,
  `ai_cfg.cfg_prompt` 운영 테이블)를 가리킨다. 저장 버튼 테스트는 **내용을 바꾸지 않은 채
  재저장**하는 방식으로만 실행했다(요청 바디·저장 UPDATE 자체는 실제로 나갔지만 content·
  page_name·output_contract 등 값은 저장 전후 동일함을 DB 직접 조회로 확인). `indicator_market`
  프롬프트의 `updated_at`만 변경되었고 내용은 원본과 동일하다.

## 2. 화면 구조 · 네비게이션 (요청 범위 1)

두 화면 모두 `app.py`의 공통 `st.navigation` 체계("AI 서비스"/"관리" 2개 섹션) 안에 있고,
제목(`st.title`)·설명 캡션(`st.caption`) 패턴은 챗봇·데이터 관리와 동일하게 따르고 있다.

- ✅ 데이터 관리(`screenshots/02_데이터관리_기본화면_비교기준.png`)는 `st.metric` 카드 +
  깔끔한 표로 완결된 한국어 UI를 제공한다. 이에 비해 요약보고서 데모·프롬프트 관리는
  "개발 데모"라는 캡션이 붙어 있긴 하지만, 실제 화면에는 영문 API 필드명이 그대로
  노출되는 부분(§3.3)이 있어 다른 "관리" 화면들보다 다듬어지지 않은 인상을 준다.
- ✅ 사이드바 연결 상태 배지(`rag_chat 연결됨`/`report_gen 연결됨`)는 챗봇·요약보고서 데모·
  프롬프트 관리 3곳에서 동일한 아이콘·문구 패턴을 쓴다 — 일관성 양호.
- 수급위기진단(stub, `screenshots/17_진단예측_stub_비교기준.png`)은 "준비 중" 안내
  배너 + 앞으로 보여줄 내용 bullet 3개로 정리돼 있어, 완성된 화면과 스타일 격차가 크지
  않다. 향후 이 화면이 실제 구현될 때 report_demo.py 톤(영문 필드명 그대로)을 따르지
  않도록 주의가 필요하다.

## 3. 요약보고서 데모 (`report_demo.py`) 상세

### 3.1 [P0] 파싱 실패 에러 아래에 이전 리포트가 그대로 남는 문제

**재현 방법**:
1. 기본 상태(광물자원가격 > 비철금속)에서 "분석요약 생성" 클릭 → `status: ok` +
   전체 분석 리포트 정상 표시.
2. observations 텍스트를 `not-json-at-all{{{` 처럼 깨진 JSON으로 바꾸고 다시
   "분석요약 생성" 클릭.
3. 화면에 `observations JSON 파싱 실패: ...` 에러 배너가 뜨는데, **그 바로 아래에 1번에서
   생성됐던 "status: ok" + 전체 분석 리포트 텍스트가 그대로 남아있다.**

증거: `screenshots/09_P0_에러아래_이전리포트잔존버그.png`

**원인(코드 확인)**: `report_demo.py`의 버튼 핸들러가

```python
if st.button("분석요약 생성", type="primary"):
    try:
        payload["observations"] = json.loads(observations_text) if observations_text.strip() else None
    except json.JSONDecodeError as exc:
        st.error(f"observations JSON 파싱 실패: {exc}")   # ← 여기서 session_state를 안 지움
    else:
        ...
        st.session_state["report_demo_result"] = client.summarize(page_id, payload)

result = st.session_state.get("report_demo_result")
if result:
    ...display...   # ← 파싱이 실패해도 이전 result가 그대로 남아 계속 렌더링됨
```

JSON 파싱이 실패하는 분기에서 `st.session_state["report_demo_result"]`를 `None`으로
초기화하지 않기 때문에, 새 요청이 실패해도 화면 하단엔 예전 성공 결과가 계속 붙어
있다. **발주처 데모 중 실수로 관측치 JSON을 잘못 고쳐서 제출하면, 에러가 떴는데도
아래에 그럴듯한 분석 리포트가 남아있어 "에러인데 결과가 나왔다"는 혼란을 준다.**

**권장**: JSONDecodeError 분기에서도 `st.session_state["report_demo_result"] = None`
추가(이미 `except ReportGenError` 분기에는 있는 처리와 동일하게 맞추면 됨).

### 3.2 [P1] Python 예외 원문 노출

같은 재현 경로에서 에러 문구가 `observations JSON 파싱 실패: Expecting property name
enclosed in double quotes: line 1 column 2 (char 1)`처럼 **Python `json` 모듈의 원시
예외 메시지**를 그대로 보여준다.

증거: `screenshots/08_JSON파싱실패_원문예외노출.png`

발주처 데모 관객(비개발자)에게는 "몇 번째 줄, 몇 번째 글자"라는 표현이 낯설고
기술적이다. 최소한 "JSON 형식이 올바르지 않습니다 — 쉼표/따옴표를 확인하세요" 같은
한 줄 요약을 앞에 붙이고, 원문은 접어서(`st.expander`) 보여주는 방식을 권장.
프롬프트 관리 화면의 output_contract 검증 에러도 동일 패턴(§4.2).

### 3.3 [P1] "페이지 고유 필드"의 영문 라벨·값 노출

`측정지표(measure)`·`수출입방향(trade_direction)`·`예측기간(forecast_horizon)`·
`가격그룹(price_group)` 같은 필드가 화면엔 `measure`·`trade_direction`·
`forecast_horizon`·`price_group`라는 **API 필드명 그대로** 라벨로 뜨고, 선택지도
`reserves`/`production`, `import`/`export`, `medium`/`long`, `base_metals`/
`minor_metals` 등 **번역 없는 영문 그대로** 노출된다.

증거: `screenshots/06_광물지도_measure필드_영문라벨.png` (핵심광물지도 > 광물지도,
"measure" 라벨에 "reserves" 선택)

나머지 화면 전체가 한국어(광종·기간·주메뉴/서브메뉴 등)로 다듬어져 있는 것과
대비되어, 이 필드들만 개발자 시점 그대로 남아있다. `report_gen_client.py`의
`PageSpec.extra_fields`가 필드명 문자열만 갖고 있어 라벨/보기용 한글 매핑이 없는
구조적 원인 — 간단한 `{"measure": "측정지표(measure)"}` 류 매핑 딕셔너리 하나로
개선 가능.

### 3.4 [P1] `compare_mineral` — 안내 없는 순수 텍스트 입력

희소금속(`price_minor_metals`)에만 있는 KOMIS "비교광종" 대응 필드
`compare_mineral`/`compare_price_criterion`이 `측정지표`처럼 특수 처리되지 않고
`else` 분기로 떨어져 **plain `st.text_input`**이 된다 — placeholder도, help
tooltip도 없다.

증거: `screenshots/05_희소금속_compare필드_안내없음.png`

바로 위 "광종" 필드는 이미 `mineral_options()`로 드롭다운(코드+한글명)을 제공하는데,
`compare_mineral`은 같은 마스터 데이터를 활용하지 않고 사용자가 `MNRL00xx` 코드를
직접 외워서 타이핑해야 한다. 데모 시연자 본인도 코드를 못 외워 매번 프롬프트관리
화면이나 DB를 봐야 하는 상황이 될 수 있음 — P1으로 분류.

**권장**: `compare_mineral`도 `mineral_options()` 드롭다운으로 교체(이미 같은 파일에
헬퍼 `_mineral_picker`가 있어 재사용 가능), 최소한 help="예: MNRL0018" 정도는 추가.

### 3.5 [P1] report_gen 리포트의 h1 제목이 페이지 제목보다 큼

리포트가 `status: ok`와 함께 `st.markdown(result["report"])`으로 그대로 렌더링되는데,
report_gen이 반환하는 마크다운 본문이 `# 텅스텐 분석 요약 — ...`처럼 h1으로 시작해
**실제 페이지 제목("요약보고서 작성 데모")보다 시각적으로 훨씬 크고 무거운 헤딩**이
결과 영역에 나타난다.

증거: `screenshots/04_요약보고서데모_결과_H1제목이슈.png`

3줄까지 줄바꿈되는 대형 타이포라 첫인상에서 "이게 페이지 제목인가?" 헷갈릴 수 있다.
프롬프트 관리의 "기능 테스트" 결과에서도 동일 패턴 재현됨
(`screenshots/16_프롬프트관리_기능테스트_H1이슈동일.png`).

**권장**: 결과를 `st.container(border=True)`로 감싸거나, 마크다운 렌더링 전 최상위
헤딩 레벨을 한 단계 낮추는 간단한 전처리(`# ` → `### `) 적용.

### 3.6 [P2] 기본 광종이 "텅스텐"

`mineral_options()`가 `ai_mnrl_mst.sort_ordr` 순으로 광종을 불러오는데, 첫 번째가
"텅스텐(MNRL0018)"이라 페이지를 열 때마다 프로젝트 5대 핵심광물(Cu·Ni·Co·Li·REE)과
무관한 광종이 기본 선택된다. 버그는 아니고 DB 정렬 순서를 그대로 따른 결과지만,
발주처 데모에서 매번 광종을 다시 골라야 하는 불편이 있다.

### 3.7 엣지케이스 — 긍정적으로 확인된 항목

- **빈 값 제출**: observations를 비우고 제출 → 크래시 없이 `status: NO_DATA` 노출.
  캡션에 "DB를 안 읽으므로 비우면 대부분 NO_DATA로 응답합니다"라고 사전 예고가 있어
  사용자가 놀라지 않는다. (`screenshots/07_빈값제출_NO_DATA_정상.png`)
- **네트워크/컨테이너 장애**: report_gen 컨테이너를 강제 종료한 상태에서 제출 →
  사이드바 배지가 즉시 "report_gen 연결 안 됨"으로 바뀌고, 버튼 클릭 시
  "report_gen 서버(http://localhost:18003)에 연결할 수 없습니다."라는 명확한 한국어
  에러가 뜬다. 크래시 없음, try/except 방어 확실. (`screenshots/10_reportgen다운_에러처리_양호.png`)
  단, 에러 안의 URL이 자동 하이퍼링크로 노출되는 점은 최종 데모 화면 기준으로는
  불필요할 수 있음(P2, 낮은 우선순위).
- **존재하지 않는 조합**: 주메뉴/서브메뉴 선택지가 전부 `PAGE_SPECS`에서 파생돼
  드롭다운으로만 고를 수 있어 애초에 "존재하지 않는 page_id"를 선택할 방법이
  UI상 없다 — 이 부분은 설계가 잘 되어 있음.

## 4. 프롬프트 관리 (`prompt_admin.py`) 상세

### 4.1 저장 → reload 흐름 (요청 범위 3)

- ✅ **긍정**: 저장 버튼 클릭 후 "DB 저장 완료"(초록)와 "report_gen 캐시 reload
  완료 — {...}"(초록)가 **분리된 두 개의 배지**로 순서대로 뜬다. 어느 단계까지
  성공했는지 명확히 구분됨. (`screenshots/15_프롬프트관리_저장reload_성공피드백_양호.png`)
- reload 실패는 코드상 "DB는 반영됐지만 report_gen 캐시 reload 실패 — 수동으로
  재시도하세요"라는 별도 경고(`st.warning`, 노란색)로 성공(초록)과 명확히 구분되게
  설계돼 있다(코드 확인, §0에서 언급한 컨테이너 경합으로 라이브 재현은 실패했으나
  report_demo.py에서 동일한 연결-실패 처리 패턴을 실제로 확인했으므로 신뢰 가능).
- [P2] reload 성공 메시지가 `{'reloaded_prompt_count': 13}`처럼 Python dict repr
  그대로 노출된다(작은따옴표, JSON 아님) — 기술적으로 보임. `json.dumps()`로 감싸거나
  "13개 프롬프트가 갱신되었습니다" 같은 자연어 문장으로 바꾸는 걸 권장.

### 4.2 [P1] JSON 검증 실패 시 DB 보호 확인 + 원시 예외 노출

output_contract 필드에 `{not valid json,,,` 를 넣고 저장 시도 →

- ✅ **긍정**: `output_contract JSON 파싱 실패: ...` 에러가 뜨고 **저장 버튼을
  눌렀음에도 실제 DB UPDATE가 실행되지 않는다**(코드상 `errors` 리스트가 비어있을
  때만 `execute_pg` 호출 — 검증 순서가 안전하게 짜여 있음). DB를 직접 재조회해
  `output_contract`가 원래 값 그대로 보존됨을 확인했다.
- [P1] 그러나 에러 메시지 자체는 report_demo.py와 동일하게 Python
  `json.JSONDecodeError` 원문을 그대로 노출한다(`Expecting property name enclosed
  in double quotes: line 1 column 2 (char 1)`). §3.2와 동일한 개선 필요.

증거: `screenshots/14_프롬프트관리_JSON검증_DB보호.png`

### 4.4 [P1] required-evidence 설계 특성에 대한 화면 안내 부재

`[[report_gen_llm_required_evidence_priority_260828]]` 메모리에 정리된 대로,
report_gen의 required `EvidenceClaim`은 페이지 content(이 화면에서 편집하는 프롬프트
본문)가 아니라 계산 로직 + 공통 프롬프트 + `output_contract`가 함께 강제하는
설계 특성이다. 즉, **사용자가 이 화면에서 content를 아무리 "간단히 써 달라"고
고쳐도 필수 근거·수치 구조는 사라지지 않는다.**

이 화면(및 content textarea 주변)을 살펴봤지만 이 설계 특성을 사용자에게 알려주는
안내 문구가 어디에도 없다. content textarea는 완전히 자유로운 텍스트 입력처럼
보이기 때문에, 사용자가 "간단하게 써줘"라고 프롬프트를 고쳤는데 리포트가 여전히
상세 수치·표를 포함하고 있으면 "프롬프트 편집이 안 먹힌다"는 재문의로 이어질
가능성이 높다(실제로 그런 재문의가 있었고, 버그가 아님을 확인한 사례가 있음 —
위 메모리 참고).

**권장**: content textarea 아래(또는 output_contract 고급 expander 안내)에
"⚠ 근거·수치 구조는 output_contract·공통 프롬프트가 함께 강제하므로, content를
간단히 써도 상세 수치·표는 유지됩니다" 정도의 한 줄 안내 추가. description 필드에
이미 있는 "⚠ 참고용 메모입니다" 패턴과 톤을 맞추면 자연스러움.

### 4.5 화면 구조 · 컨트롤 (요청 범위 1·2)

- `[공통]`(summary_common) 선택 시 "이 프롬프트는 12개 리포트 화면 전체의 공통
  서두에 적용됩니다 — 아래에서 대표로 확인할 화면을 1개 고르세요"라는 안내가
  뜨고, 대표 페이지 선택 드롭다운이 자연스럽게 나타난다 — 설계 의도가 화면에
  잘 반영됨. (`screenshots/12_프롬프트관리_공통선택.png`)
- description 필드 옆 `?` 도움말 아이콘에 "report_gen이 이 컬럼을 읽지 않아 실제
  분석요약 결과엔 영향이 없습니다"라는 경고가 이미 잘 붙어 있음 — 이런 패턴을
  §4.4의 required-evidence 안내에도 그대로 적용하면 됨.
- [P2, 낮은 우선순위·버그 아님] 상단 `prompt_key` 선택은 report_demo.py와 동일한
  주메뉴/서브메뉴 2단 콤보박스로 통일됐지만, "등록된 프롬프트 목록" expander의 표와
  "기능 테스트 > 테스트할 페이지 선택" 드롭다운은 옛 "주메뉴 > 서브메뉴 (id)"
  문자열 조합 1단 형식을 그대로 쓴다. 코드 주석(`prompt_admin.py` 34-36줄)에 "이번
  요청 범위 밖"이라고 명시돼 있어 의도된 보류이지만, 한 화면 안에서 상호작용
  패턴이 2가지로 혼재하는 점은 다음 통일 작업 후보로 기록해둔다.
- "이 프롬프트로 분석요약 호출" 기능 테스트는 report_demo.py와 동일한 클라이언트를
  재사용해(`PAGE_SPECS` 공유) 동일한 필드 구성·타이밍으로 동작함을 확인했다. §3.5의
  h1 제목 이슈도 여기서 동일하게 재현된다(`screenshots/16_프롬프트관리_기능테스트_H1이슈동일.png`).
