`DAY`/`WEEK`/`MONTH`/`YEAR`의 `flctnPrcnt` 값 -0.70 / **0.98** / **5.11** /

— 즉 **KOMIS 서버가 이 4개 비교값을 이미 계산해서 같은 응답에 실어 준다.**
raw 캡처 전체는
`report_gen_price_base_metals_부실요약_원인조사_260828_evidence/live_copper_lme3m_getMnrlPrcByMnrkndUnqCd_raw_260828.json`에
보존(META.md 동봉).

그런데 기존 어댑터(`komis_dump_smoke_test.py::adapt_price_pages()`,
`komis_live_playwright_test.py::_adapt()`) 둘 다 `resp_body["dataAvg"]`에서
**`INFO` 키만** 읽고 `stdMap`은 아예 참조하지 않는다(코드 확인:
`info = (resp_body.get("dataAvg") or {}).get("INFO") or {}` — 이 줄이 전부).
그 결과 report_gen은 KOMIS의 전주/전월/전년 비교값을 받아본 적이 없고,
`komir_summary.py::_avg_before(7)`(롤링 7일 창 평균)로 **스스로 다시
계산**한다 — 그래서 두 숫자가 다르게 나온 것이다.

### KOMIS 산식 정의 — 캡처된 673행 실측치로 직접 계산해 확정(추론 아님)
지난 조사에서 "미해결"로 남긴 "정의 차이 vs 데이터 차이"(당시엔 합성
데이터를 썼다는 이유로 판정을 유보했다)를, 이번엔 라이브 캡처에 같이
들어있는 동(LME 3개월) 673행 전체 원본 일별 가격으로 직접 재계산해
확정했다(추정이 아니라 계산 결과):

```
KOMIS 응답의 implied 평균 = 기준가격(14,236.00) - flctnPrc
  전주평균 implied = 14,236.00 - 137.90 = 14,098.10
  전월평균 implied = 14,236.00 - 692.07 = 13,543.93
  전년평균 implied = 14,236.00 - 4,269.49 = 9,966.51

같은 673행에서 후보 창별로 실제 평균을 계산:
  직전 완결 역주(월~금, 2026-08-17~08-21) 5거래일 평균
    = (14315.00+14080.00+13890.00+13970.50+14235.00)/5 = 14,098.10  ← implied와 소수점까지 정확히 일치
  롤링 7일창(08-20~08-26, 우리 _avg_before(7) 방식) 평균 = 14,216.90  ← implied와 다름(=118.80 차이)
  2026년 7월 전체(23거래일) 평균 = 13,543.93  ← implied와 정확히 일치
  2025년 전체(253거래일) 평균 = 9,966.51  ← implied와 정확히 일치
```

**세 기간 모두 실측 데이터로 소수점 둘째자리까지 정확히 일치** —
KOMIS의 "전주평균/전월평균/전년평균"은 **직전으로 완결된 역주(월~금)/
역월/역년의 전체 일평균**이고, `komir_summary.py`의 `_avg_before(7)`
(오늘 기준 롤링 7일 창)와는 서로 다른 산식임이 확정됐다. 참고로 롤링
7일창(14,216.90)은 이전 조사에서 합성 데이터로 얻은 값(+0.13%, 당시엔
"합성치라 다르다"로 적었던 것)과 사실상 같은 결과다 — 즉 지난번 +0.13%도
합성 데이터 아티팩트가 아니라 **처음부터 산식 차이**였다(위쪽 "(a) 검증
2" 절의 "합성 구간이 섞여" 서술은 이 재확인으로 정정한다: 데이터 문제가
아니라 산식 문제).

### 함의 — 산식을 맞춰 재구현할 필요 없이 KOMIS 제공값을 그대로 읽으면 된다
정의 자체는 위에서 확정됐지만("직전 완결 역주/역월/역년 평균"), 그걸
`komir_summary.py`에 재구현할 필요는 없다 — **KOMIS가 이미 계산해서

대신 이 값을 우선 사용하도록 설계하면 KOMIS 웹사이트 표시값과 100% 일치를
보장할 수 있다. (설계·구현 여부는 결정 필요 — 아래 종합 판정 참고.)

### 덤으로 확인된 것 — 재고량(inventory) 원천은 이미 파싱되고 있다
같은 라이브 응답의 `data.defaultMnrl` 일별 행에는 `invt`(재고량 원값)
외에 `invtPrc`(전일대비 재고 증감량)·`invtPrcnt`(전일대비 재고 증감률)도
있다(예: `{"crtrYmd": "20240104", "invt": "164450.00", "invtPrc": "72.00",
"invtPrcnt": "0.11", ...}`). `adapt_price_pages()`/`_adapt()`는 이미
`inventory: _num(row.get("invt"))`로 `observations`에 담고는 있다 — 즉
**원천 파싱은 이미 존재**한다. 앞서 확인한 (b) 구조적 공백(재고량이
`komir_summary.py` 계산 로직·프롬프트에서 전혀 안 읽힘)은 이번 재확인으로도
불변이지만, "재고량 데이터가 아예 없다"가 아니라 "관측치에 담겨서 들어와도
계산기가 안 읽는다"는 점이 한 번 더 확인됐다 — 재고량 지원을 추가하기로
결정되면 `invtPrcnt`(KOMIS 자체 재고 등락률)도 price와 같은 패턴으로
그대로 활용 가능하다.

어디에도 "재고량"이라는 단어가 없다** — 발주처가 정의한 "요약 답변"
계약 자체가 재고량을 요구하지 않는다. 즉 이 공백이 "PDF 계약 미달"인지
"KOMIS 화면엔 있지만 요약 답변 스펙 밖이라 의도적으로 제외"인지는 이
조사만으로는 판정 불가 — 결정이 필요한 지점.

## 일별 상세 테이블(7행 그대로 나열)에 대해
PDF §1-1 문형("[광종] 가격은 [현재가격]으로 전주 대비...전월...전년동기...
했습니다. 가격 변동의 주요 요인으로는...")은 압축된 3~4문장 요약이지,
일자별 나열을 요구하지 않는다 — KOMIS 화면의 "일별 상세 테이블"은
요약 답변과 별개인 원자료 표(UI 위젯)로 보인다. 따라서 이 부분은
report_gen "요약"의 미달로 보기 어렵다(PDF 스펙 자체가 안 요구).
