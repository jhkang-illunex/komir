## 1. 어투 — 격식체 통일

**룰**: "어투: 격식체(~습니다) 통일"

**실측**: 문서 Q&A 경로 15건 전부(t1~t9, near-miss 포함, 다중턴 포함) 답변이
`~습니다/~합니다`로 끝났고 반말·해요체 사용례를 찾지 못했다. 예:

- "코발트(CO)의 최근 수급위기 진단 등급은 '주의'입니다." (t5_cause)
- "제공된 문서에서 근거를 찾지 못했습니다." (t8a_offtopic, 기권 응답도 격식체 유지)
- near-miss 응답도 "…자료라도 보여드릴까요?" 로 어미 통일(NEAR_MISS_SYSTEM_PROMPT에
  별도 격식체 지시가 있어 일관됨).

page_recommend 경로(t6_rawdata, t7_menu)는 완결된 문장 대신 `라벨: 값` 목록·
명사구 나열 스타일(예: "확인할 점:", "화면 사용:")이라 격식체/반말 판정 대상
문장 자체가 적고, 위반 사례도 없었다. 룰이 요구하는 "통일"의 취지(불특정
사용자 대상 공손함 유지)에는 부합하나, 문서 Q&A 경로와 스타일이 다르다는 점만
기록해둔다.

**판정**: 준수. 수정 불필요.

## 2. 출처 footer

**룰**: "모든 답변에 데이터 출처 기본 표기, 상세는 [근거 데이터 보기] 패널로
표출"

**실측 — 본문 footer는 정확**: `_source_footer()`(chatbot.py:310)는 실제
인용된 `[n]`만, `(source, section, as_of)` 중복 제거해 나열한다. 예(t1_table):

```
출처:
[7] USGS Mineral Commodity Summaries USGS_2026 · LITHIUM · 국가별 세계 생산량
```
본문에서 `[7]` 하나만 인용됐고 footer도 `[7]` 하나만 — 정확히 일치.

**실측 — 그러나 "[근거 데이터 보기]" 패널(=`done.citations` 필드)은 과다 노출**:
`_citation_sources()`(chatbot.py:302)는 `cited_indices`로 필터링하지 않고
검색된 evidence 전부를 돌려준다. 같은 t1_table 예시에서 `done.citations`에는
9건이 실렸다(index 1~9 전부) — 본문에서 실제로 언급한 건 `[7]` 하나뿐인데
나머지 8건(생산매장량 USGS 2024/2025/2026 Reserves7, 조달청 구리 동향 등,
질문인 "리튬 수입 상위국"과 무관한 문서 포함)도 패널에 그대로 노출된다.

프런트(`inhouse/streamlit_demo/chatbot.py:183-186`)는 이 필드를 그대로
`인용 근거 N건` expander로 렌더링한다 — 즉 사용자가 "근거 데이터 보기"를
열면 실제로 답변에 쓰이지 않은 근거까지 "근거"로 표시된다. 룰의 "상세는
[근거 데이터 보기] 패널로 표출"은 문맥상 본문에 표기한 출처의 상세이지,
검색은 됐지만 답변엔 안 쓰인 자료까지 포함하라는 의미로 보기 어렵다.

**왜 이렇게 됐는지**: `_source_footer`는 `cited_indices`로 필터링하는데
`_citation_sources`는 필터링 로직이 아예 없다 — 같은 데이터(evidence 리스트)를
두 함수가 다른 기준으로 가공하면서 생긴 불일치로 보인다(의도적 설계라기보다
구현 시 footer만 필터링을 추가하고 done 페이로드는 손대지 않은 것으로 추정).

**수정 제안**: `chat_turn()`에서 `citation_sources = _citation_sources(evidence)`
호출 시 `cited_indices`를 넘겨 `_citation_sources(cited_indices, evidence)`처럼
인용된 것만 남기거나, 최소한 `cited: bool` 플래그를 각 항목에 추가해 프런트가
구분해 표시할 수 있게 한다.

**판정**: 부분준수 — 본문 footer는 정확, 상세 패널(citations 필드)이 룰 취지와
어긋남.

## 3. 주의문구(_caution_notice)

**룰(유형5)**: "출력 ⇒ 진단지표(정형) + 관련 문서(RAG 검색) + 주의 문구 + 원문
링크" / "유의 ⇒ 인과 단정 금지, 동시 발생 흐름으로 서술"

**실측 — 정상 발동 사례** (`t_caution_probe`, "니켈 수급위기 진단등급이 어떻게
되고, 최근 인도네시아 수출 정책 관련 문서도 근거로 같이 인용해서 설명해줘"):
본문에 구조화 진단(`[1]`, kind=structured)과 문서 근거(`[3][4]`, kind=dense)가
함께 인용되자 문구가 정확히 붙었다.

```
※ 위 설명은 지표 변동과 동시에 나타난 문서상 흐름을 정리한 것으로,
직접적인 인과관계를 단정하는 내용이 아닙니다.
```

이 경우는 룰이 원하는 형태(진단지표+관련문서+주의문구)를 정확히 재현한다.

**실측 — 미발동 사례** (`t5_cause`, 룰 원문의 유형5 예시 질문 그대로
"코발트 수급동향지표 등급이 왜 '주의'로 바뀌었어?"): 본문에 구조화 진단
`[1]`만 인용되고 문서 근거는 검색은 됐지만(evidence 2~7건) 본문에 인용되지
않아 주의문구가 **붙지 않았다**.

**원인**: `_caution_notice()`(chatbot.py:335)는 `cited_kinds`에 `structured`와
그 외(dense/pageindex)가 **함께** 있을 때만 문구를 붙인다(343-344행:
`if "structured" in cited_kinds and cited_kinds - {"structured"}`). 구조화
진단 하나만 인용되고 문서 근거는 인용에 실패(모델이 관련 문서를 찾았어도
답변에 반영하지 않음)하면 조건이 성립하지 않는다. 그런데 이 사례가 바로
룰 원문이 유형5의 대표 예시로 든 질문이라, 가장 흔히 나올 답변 형태에서
문구가 빠지는 셈이다.

**수정 제안**: 트리거 조건을 "structured+dense/pageindex 동시 인용"에서
"structured 중 `latest_diagnosis`류(등급·위험점수 진단) 인용 시 무조건"으로
넓힌다 — 등급 변화 자체를 설명하는 문장은 문서 근거 유무와 무관하게 인과
단정 오인 소지가 있다. §7의 "사유" 라벨 문제와 함께 처리하면 한 번에
해결된다.

**판정**: 부분준수 — 메커니즘 자체는 정확히 동작하나 트리거 조건이 룰의 대표
예시 케이스를 놓친다.

## 4. status 1~4 단계 SSE 이벤트

**룰**: "1.질문 조건 확인 2.답변 준비중 3.데이터 분석 중 4.답변 생성 중"
(순서·재시도 왕복 명시는 없으나 위 4단계가 실제로 오는지 확인 필요)

**실측**: 문서 Q&A 경로 15건 전부 `1 → 2 → 3 → 4` 순서를 지켰고, 재조회
(reformulate)가 발생한 경우 `3 → 2 → 3` 왕복 후 `4`로 수렴하는 패턴이
반복 확인됐다(t1_table, t3_trend, t4_compare, t5b_cause2, t8a_offtopic,
t9_other 등: `[1, 2, 3, 3, 2, 3, 4]`). 근거가 명확히 한 번에 잡힌 경우는
왕복 없이 `[1, 2, 3, 4]`(t5_cause, t8b_unsupported_commodity,
t_caution_probe). page_recommend 경로는 설계대로 `[1, 4]`만 온다(t6_rawdata,
t7_menu) — 중간 단계를 안 쪼개는 것은 코드 주석에 명시된 의도된 동작.

프런트 관점에서 이상 여부: 라벨 문구가 겹치는 재조회(`3`이 반복)나 단계
후퇴(`3→2`)가 있어도 매번 유효한 stage 값(1~4)이라 프런트가 "진행률 역행"
처럼 보일 수는 있지만 계약 위반은 아니다 — 원문 독스트링에도 "재시도 시 3이
여러 번 올 수 있음"으로 명시돼 있다.

**판정**: 준수. 수정 불필요.

**룰(유형8)**: 범위 밖 질문에 사유별 문구 4종 필요 —
- 지원 범위 밖(광물 무관): "광물 관련 정보만 조회 가능"
- 지원 광종 밖: "유사 광종(OO) 조회 가능 안내"
- 기간 데이터 없음: "조회 가능 기간(YYYY.MM.DD~YYYY.MM.DD) 안내"
- 질문 모호: "광종/기간/수입·수출/생산량·매장량 등 구분 요소 재확인 요청"

**실측 — 사유 분류가 사실상 작동하지 않음**: `_classify_abstain()`(정확한
사유별 문구를 만드는 LLM 분류기)은 `chat_turn()`에서 **검색 결과(evidence)가
0건일 때만** 호출된다(chatbot.py:516). 그런데 실제로 범위 밖 질문도 "니켈",
"가격" 같은 키워드가 있으면 dense/pageindex 검색은 대부분 뭔가를 찾아온다
— 즉 evidence는 0건이 아니고, 생성 LLM이 CHATBOT_SYSTEM_PROMPT 규칙4("근거가
전혀 없으면 ABSTAIN_TEXT")에 따라 스스로 기권한다(chatbot.py:562). 이 경로는
`abstain_reason="unknown"`으로 고정되고 사유별 문구 자체가 생성되지 않는다.

실제 캡처된 사례:

| 질문 | 기대 사유(룰) | 실제 status | 실제 답변 | abstain_reason |
|---|---|---|---|---|
| "니켈 관련주 지금 사도 될까?" (룰 원문 유형8 예시) | off_topic | 1→2→3→3→2→3→4 (status 4까지 도달 = evidence 있었음) | "제공된 문서에서 근거를 찾지 못했습니다." | **unknown** |
| "주석(Sn) 가격 알려줘" | unsupported_commodity(유사 광종 안내 필요) | 1→2→3→4 | "제공된 문서에서 근거를 찾지 못했습니다." | **unknown** |
| "핵심광물 시장에 대해 재미있는 이야기 하나 해줘" | (유형9, 범위밖은 아니지만 참고) | 1→2→3→3→2→3→4 | 동일 정형 문구 | **unknown** |

세 사례 모두 status가 4까지 진행됐다는 것 자체가 검색은 성공(evidence≠0)했다는
뜻이라, `_classify_abstain()`의 4종 사유 분류(그리고 그에 맞는 안내 문구)가
전혀 호출되지 않았다. 룰이 원문 예시로 든 "니켈 관련주 지금 사도 될까?"에서
조차 "광물 관련 정보만 조회 가능"이라는 지정 문구가 나오지 않고 일반
ABSTAIN_TEXT("제공된 문서에서 근거를 찾지 못했습니다")만 나온 것은 룰 5번
항목(주의 문구)이 아니라 룰 8번 항목(사유별 안내)의 명백한 미이행이다.

**추가 발견 — "질문 모호" 케이스는 아예 반대로 동작(더 심각)**: "가격
알려줘"(광종·기간 모두 미지정, 룰이 정의한 전형적 "질문 모호" 케이스)를
보냈더니 시스템은 되묻지 않고 **금(Gold)·인듐(Indium) 가격 데이터로 답변을
생성**했다(t8d_ambiguous). 5개 지원 광종(CU/NI/CO/LI/REE)에 전혀 속하지 않는
광종 데이터를 인용 규율(오직 [근거]만 인용)은 지키면서도 태연히 표까지
만들어 제시한 것이다:

```
| 광종 | 가격 정보 | 기준 시점 | 근거 |
| Gold (금) | $1,363.96 per troy ounce | 2018년 1월 25일 | [4] |
| Indium (인듐) | $220 per kilogram | 2021년 | [6] |
```

**원인**: `_classify_abstain`이 전혀 호출되지 않았고(evidence 6건 존재),
CHATBOT_SYSTEM_PROMPT에는 "5개 지원 광종 밖이면 거절하라"는 지시가 없다 —
규칙 1~10(chatbot.py:164-179) 어디에도 광종 화이트리스트 제약이 없다.
검색이 "가격"이라는 단어로 USGS 문서 중 금·인듐 관련 섹션을 근거로 끌어오면
LLM은 그걸 정당한 [근거]로 보고 그대로 답한다. 즉 유형8의 "지원 광종 밖"
가드는 evidence=0인 극히 좁은 경우에만 작동하고, evidence가 있으면(다른
광종이라도) 전혀 걸러지지 않는다.

**왜 문제인가**: 룰이 요구하는 8번 유형의 실사용 빈도가 높은 케이스(광종
언급 없이 "가격 알려줘" 같은 모호한 질문, "관련주 사도 되나" 같은 범위 밖
질문)에서 정확히 실패한다. 반면 `_classify_abstain`이 실제로 작동하는
"evidence 0건" 상황은 흔치 않다(코퍼스가 넓어 어떤 질문이든 뭔가는 걸림).

**수정 제안**:
1. `_classify_abstain` 호출 조건을 "evidence=0"에서 "생성 결과가
   ABSTAIN_TEXT인 경우(현재 abstain_reason='unknown'으로 고정되는 경로,
   chatbot.py:562-573)에도" 확장한다 — 이 경로가 실제로는 더 자주 발생하는
   유형8 케이스다.
2. CHATBOT_SYSTEM_PROMPT 또는 검색 단계에 "5개 지원 광종(CU/NI/CO/LI/REE)
   밖의 광종이 [근거]에 있어도 그 광종을 주된 답으로 쓰지 말라"는 명시적
   가드를 추가한다 — 현재는 인용 규율(근거 기반)만 있고 광종 화이트리스트
   가드가 없어 범위 밖 광종도 "정당한 근거"로 취급된다.
3. "질문 모호"(광종/기간 등 특정 불가) 케이스는 evidence 유무와 무관하게
   질문 자체의 필수 조건(광종) 결여를 사전에 감지해 되묻는 별도 체크가
   필요하다 — 현재는 검색이 우연히 아무 광종 데이터나 찾아오면 그걸로
   답해버린다.

**판정**: **위반**. 룰 원문이 유형8의 대표 예시로 든 질문("관련주 사도
되나")조차 지정 문구가 안 나오고, "질문 모호" 케이스는 되묻기는커녕 범위
밖 광종 데이터로 답변까지 생성한다 — 8번 항목 중 가장 심각한 이탈.

## 7. 원인·인과 단정 회피

**룰(유형5 유의사항)**: "인과 단정 금지, 동시 발생 흐름으로 서술"

**실측 — 위반 사례**(t5_cause, 룰 원문 유형5 예시 질문 그대로):

```
* **사유**: 국제 핵심광물 시장의 가격 변동성 급증 [1]
```

"사유"라는 단어 자체가 인과관계를 단정하는 표현이다. 코드를 추적한 결과 이
문구는 챗봇 LLM이 지어낸 것이 아니라 **정형 근거 텍스트 자체에 이미 포함된
템플릿**이었다 — `inhouse/services/shared/retrieval/evidence.py:77`:

```python
text = (
    f"{commodity_code} 최근 수급위기 진단 등급: {row.get('alert_level')} "
    f"(위험점수 {row.get('risk_score')}, 사유: {row.get('reason')})"
)
```

즉 진단 모델(msr)이 산출한 위험요인 텍스트를 담는 DB 컬럼/필드 라벨 자체가
"사유"다. 챗봇은 인용 규율(오직 [근거]만, 발췌문에 없는 결론 지어내기 금지)을
충실히 지켜 이 라벨을 그대로 옮겼을 뿐이라, **챗봇의 인과-단정-회피 규칙 9번
(CHATBOT_SYSTEM_PROMPT, chatbot.py:175-176)이 실패한 게 아니라 상류(정형
근거 생성 단계)에서 이미 "사유"라는 단정적 라벨을 심어놨다**는 게 근본
원인이다. §3의 주의문구 미발동(구조화 데이터 단독 인용 시)과 겹치면 룰
유의사항이 이중으로 새는 셈이다.

**실측 — 정상 사례**(t_caution_probe): 문서 근거가 함께 인용된 경우엔
"~를 강화함", "~에 초점을 맞추고 있으며"처럼 사실 서술형으로 나오고 주의문구도
붙어 룰 취지에 맞았다 — 즉 문제는 구조화 진단이 단독 인용될 때 그 근거
텍스트 자체("사유:")에 있다.

**수정 제안**: `evidence.py:77`의 라벨을 "사유"에서 "주요 변동 요인"·"기여
요인" 등 인과 단정이 아닌 표현으로 바꾼다(챗봇 프롬프트 수정보다 근본
원인에 더 가까운 수정). §3 제안(주의문구 트리거 확장)과 함께 적용하면
구조화 진단 단독 응답에도 "인과 단정 아님" 문구가 자동으로 붙어 이중 안전장치가
된다.

**판정**: 부분준수 — 챗봇 자체 로직은 룰을 지키려 했으나(인용 충실), 근거
데이터 생성 단계의 "사유" 라벨이 룰 유의사항과 충돌한다.

## 8. 이동 안내(page_recommend)

**룰(유형7)**: "출력 ⇒ 계층형 텍스트 경로(예: KOMIS > 핵심광물지도 >
광물지도) + 관련 메뉴 링크(상세 링크 추가) + 이동 안내('바로 이동하시겠어요?')"

**실측**(t7_menu, "광물지도는 어디서 볼 수 있어?" — 룰 원문 유형7 예시
질문과 거의 동일):

```
추천 페이지는 `KOMIS > 핵심광물지도 > 광물지도`입니다.
...
페이지 주소: https://www.komis.or.kr/Komis/MnrlMap/MnrlMap
...
바로 이동하시겠어요? 위 페이지 주소를 눌러 이동하실 수 있습니다.
```

계층형 경로 표기("KOMIS > 핵심광물지도 > 광물지도")·상세 URL·이동 안내 문구
("바로 이동하시겠어요?") 세 요소가 룰 예시와 표현까지 거의 일치한다. 필터
기본값 안내("별도 언급이 없어 적용한 기준: …"), 로그인 필요 여부, 데이터
공백 가능성 등 부가 안내도 자연스럽게 붙어 실사용성이 높다.

유형6(원자료 요청, t6_rawdata: "니켈 수급동향지표 전체 데이터 보여줘")도
같은 page_recommend 경로를 탄다. 룰이 지정한 문구는 "해당 화면에서 전체
데이터를 확인하실 수 있습니다"처럼 짧은 안내인데, 실제로는 유형7과 동일하게
페이지 상세 설명·화면 구성·확인할 점까지 길게 나온다 — 정보량은 룰 요구를
상회하지만, 룰이 원하는 간결한 "전체 데이터 안내" 톤과는 다소 결이 다르다.
다만 이 자체를 위반으로 보긴 어렵고(과소가 아니라 과다 제공), 유형6과 유형7이
사실상 같은 렌더러를 공유해 구분되지 않는다는 점만 기록해둔다.

**판정**: 준수 — 유형7은 룰과 표현까지 일치. 유형6은 문구가 룰보다 장황하나
위반이라 보기 어려움(참고 사항).

### 원인 확정(실측)

먼저 "부족한지 로그로 실측 확인" 지시대로, `OpenAICompatChat.complete()`를
컨테이너 안 격리 프로세스에서 몽키패치해 verify 호출의 HTTP 응답 원문
(`finish_reason`·`usage.completion_tokens`)을 직접 캡처했다(docker cp로 원본
`chatbot_graph.py`는 건드리지 않고 조회만, 이후 원복). "코발트 광물종합지표의
최근 12개월 변화를 보여줘"를 6회 반복 실행한 결과:

| 결과 | `finish_reason` | `completion_tokens` |
|---|---|---|
| 성공(파싱 정상) | `stop` | 87~144(최대 144) |
| **실패(JSON 파싱 에러 재현)** | **`length`** | **정확히 150(=max_tokens 상한)** |

실패 사례는 예외 없이 `finish_reason="length"`이자 `completion_tokens`가
`max_tokens=150`과 정확히 일치했다 — JSON 포맷팅 버그가 아니라 순수
토큰 상한 부족이었다. 원인: 근거가 reformulate 이후 9건까지 늘어나면
verify LLM이 "1) 근거1은 ~, 2) 근거2는 ~, 3) ~"처럼 근거별로 불충분 사유를
나열하는 습성이 있어, 그 설명이 자연스럽게 150 토큰을 넘긴다. 복구
재시도(2차 호출)도 같은 `max_tokens=150`을 쓰므로 똑같이 잘리고, 결국
`LLMOutputError` → 안전 폴백 `sufficient=True`인데 evidence가 이미 비어
있어(또는 재구성 안 됨) 하류(`chat_turn`)가 완전 기권으로 끝났다.

### 수정

`chatbot_graph.py::_verify_node`의 `max_tokens`를 150 → **300**으로 상향
(성공 사례 최대치의 약 2배 여유). 다른 두 LLM 호출(route=160,
reformulate=80)은 원래도 실패 사례가 없어 손대지 않았다 — 최소·외과적
변경 원칙.

| 실행 | mode | 결과 |
|---|---|---|
| 1회차 | **document** | 분류된 기권 — `abstain_reason="ambiguous"` + "…조금 더 구체적으로 말씀해 주시면 답변드릴 수 있습니다." |
| 2회차 | **document** | 정상 응답 — `geo_index_trend(CO)` 주간 지수표 생성 |
| 3회차 | **document** | near-miss — "…자료는 존재하지 않습니다. 다만…이 자료라도 보여드릴까요? [1]" |

3회 전부 `mode=document`로 확인됐다(`page`로 새는 경우 0/3) — main-agent가
직접 재현한 회귀(3/3 `price_minor_metals` 오추천)가 해소됐다. 3회의 세부
결과가 갈리는 것(분류된 기권/정상 응답/near-miss)은 라운드1·2가 이미
정상으로 판정했던 것과 같은 양상이라 문제 삼지 않는다.

### [5] 커밋 전 재검증에서 발견 — 예외 초안이 룰 원문 예시 2건을 새로 깨뜨림(자체 발견·수정)

위 [1]~[4]로 목표는 달성됐다고 판단했으나, 커밋 전 한 번 더 광범위하게
경계를 확인하는 과정에서 **이 예외 초안이 chatbot_rule.txt 원문의 다른
예시 질문 2건을 새로 오분류시킨다는 걸 자체 발견**했다:

| 질문 | 예외 초안 분류 | 문제 |
|---|---|---|
| "니켈 수급동향지표 전체 데이터 보여줘"(**유형6 원문 예시**, 원 감사 §0/t6_rawdata에서 page→`indicator_supply`로 정상 처리돼 §8을 "준수"로 판정한 근거) | **document로 오분류(3/3)** | "수급동향지표"가 예외 트리거 단어에 걸려 유형6이 요구하는 "전체 데이터 메뉴 링크 + 안내 문구" 대신 RAG 문서 검색으로 새 버렸을 것 — §8의 기존 "준수" 판정과 정면으로 모순되는 새 회귀 |
| "핵심광물지표는 어느 메뉴에서 확인할 수 있어?"(**유형7 두번째 원문 예시**) | page/document 실행마다 불안정(3회 중 1회 document) | 명백히 "어느 메뉴"를 묻는 질문인데도 "핵심광물지표"라는 지표 이름 때문에 예외가 간헐적으로 발동 |

원인: 예외 규칙이 "질문에 합성지수 이름이 들어있는가"만 보고 "질문이
실제로 뭘 원하는가"(전체 데이터를 통째로 달라 / 메뉴 위치를 묻는다)는
안 봐서 과잉 적용됐다. **이 두 건은 main-agent의 지시 범위에 없던 것을
이 세션이 자체 회귀 테스트로 찾아낸 것**이라 별도 지시 없이 코드
수정까지 진행했다 — 좁히는 방향의 안전한 보정이고, 라운드3·4가 이미
구축한 검증 하네스로 즉시 전수 재검증이 가능했기 때문이다.

**수정**: `INTENT_PROMPT`에 "예외의 예외"를 추가했다 — 합성지수 질문이어도
(1) 화면 위치 자체를 묻거나, (2) "전체 데이터"·"원자료"를 통째로
요청하면 여전히 page다.

**재검증**: 라운드4 §3의 20개 케이스에 이 두 경계 질문을 더해 **22개
케이스를 3회 반복** 재분류 — 3회 전부 완전히 동일했고, 목표(고정질문#3
+ 변형 4개는 document, 니켈가격·리튬수입국 등 라운드3 6건은 page 유지)와
이번에 새로 발견한 2건(유형6 원문 예시·유형7 원문 예시 둘 다 page로
정상 복귀) 전부 기대대로 나왔다. `_run_chat()` end-to-end로도 재확인:

| 질문 | 실행 3회 | 결과 |
|---|---|---|
| "코발트 광물종합지표의 최근 12개월 변화를 보여줘"(목표) | 3/3 | `mode=document` 유지 |
| "니켈 수급동향지표 전체 데이터 보여줘"(유형6, 새로 발견한 회귀) | 3/3 | `mode=page`, 추천 page_id=**`indicator_supply`**(원 감사와 동일) |

커밋에는 이 최종(예외의 예외 포함) 버전만 반영했다 — 초안 단계에서
멈추지 않고 발견 즉시 좁혀서 룰 원문 예시 전체가 기대대로 동작함을
확인한 뒤 진행했다.
