## 2. 작업 1 — 외부 저장소(komis-report-generator-main) 병합

사용자(프로젝트 관리·개발 담당, 팀원 퇴사로 단독 핸들링 전환)의 요청으로 별도
저장소의 RAG/리포트 생성 구현을 검토 후 병합. 착수 전 실사 결과, 실제로 완성돼
동작하던 건 **페이지·필터 추천 챗봇 하나뿐**이었고 RAG 벡터검색·리포트 생성 로직은
전부 스텁이거나 미배선 상태였음을 먼저 확인·문서화(`병합계획_komis-report-generator_260811.md`).

### 병합 결정 3건과 실행 결과
| 결정 | 실행 |
|---|---|
| ① 페이지추천을 RAG 챗봇 기능 일부로 편입 | LangGraph 그래프를 `rag_chat/app/page_recommend/`로 이식, `/chat`에 `mode=document\|page\|auto` 3경로 배선 |
| ② komir 스텁에 코드 직접 이식(서비스 단위 아님) | `services/{shared,ingestion,rag_chat,report_gen}` 4개 패키지 실구현 |
| ③ PDF 파싱은 komir 자체 구현이 정본 | 외부 repo의 PyMuPDF 파서 대신 기존 opendataloader+OCR 폴백 체인 재사용 |

### 만들어진 것
- **`services/shared/`**: 설정(`config.py`, pydantic-settings 단일 로더)·DB 접근(`db.py`)·LLM 클라이언트(`llm_client.py`, `KomirJsonLLM`)·정형조회(`retrieval/structured.py`, rag_chat·report_gen 공용) — 서비스 3종의 공통 기반. 이전에는 LLM/임베딩 설정이 서로 연계돼 있지 않았던 것(외부 repo가 별도 클라이언트를 갖고 있었음)을 이번에 하나로 통합.
- **`services/ingestion/`**: PDF/HWP → 정규화 마크다운 추출 파이프라인(pydantic 계약, 해시 기반 중복제거). HWP는 신규 capability(pyhwp 구조 파서), PDF는 komir 기존 체인 재사용.
- **`services/rag_chat/`**: `POST /chat` — 문서 Q&A(인용강제 생성+SSE 스트리밍) + KOMIS 43개 페이지 추천, 실제 vLLM 서버로 end-to-end 검증(토큰 스트리밍·환각 없는 기권 응답 확인).
- **`services/report_gen/`**: 템플릿×정형데이터 → 리포트 본문 조립 → `out_report` 적재. 5광종 리포트 생성·API 노출까지 실동작 확인.

### 검증 방식(전 구간)
`python3 -m py_compile` 전체 통과는 기본이고, 매 단계 **실제 DB 조회·실제 API 호출·실제 문서로 end-to-end 스모크 테스트**를 거쳤다(문서/코드 예시를 그대로 믿지 않고 직접 확인하는 프로젝트 원칙 적용).

### 병합 과정에서 실측으로 발견·수정한 버그(신뢰성 관련, 별도 기록)
| # | 내용 | 발견 방법 |

## 3. 작업 2 — PostgreSQL 벡터 저장소(pgvector) 채택

### 벡터DB 결정 재정정
2026-08-05 "Qdrant 확정, pgvector 폐기"(사유: Postgres는 외부서비스라 확장 설치
권한 보장 없음)였으나, **실측 결과 komis_demo DB에 pgvector 0.8.2가 이미 설치돼
있고 접속 계정도 슈퍼유저**임을 확인 — 우려했던 리스크 자체가 없었다. Qdrant
컨테이너를 새로 띄우지 않고 이미 연결된 Postgres에 벡터 컬럼을 추가하는 방향으로
결정 변경(`CONTAINER_ARCHITECTURE.md` §0 정정 반영).

### 만들어진 것
- `data_lake/db/schema_pgvector.sql` — `mineral_risk.doc_chunk`에 `embedding vector(384)` + HNSW 인덱스 추가(public 스키마는 무오염 확인).
- `rag/ragkit/build_pgvector_index.py` — documents/산출물 76건 임베딩 적재.
- `services/ingestion/build_pgvector_okf.py`(신규) — 대용량 보고서(문서-OKF 소스) 임베딩 적재, 기존 파이프라인과 별개 `src` 컬럼으로 안전하게 공존.

### 검증
회귀 비교 질의 3건(pgvector vs 기존 DuckDB 검색) **전부 top-5 완전일치**(순위까지 동일) — 벡터 저장소를 옮겨도 검색 품질이 그대로임을 확인.

## 4. 작업 3 — 문서-OKF·PageIndex·pgvector 코퍼스 확장

### 배경
RAG 코퍼스가 `documents/산출물` 76건에 한정돼 있던 것을, 발주처 데이터인 **USGS
생산매장량 보고서·조달청 비철금속 시장동향 보고서·Argus 비철금속 일일 시황**까지
확장. "문서-OKF"(원문 전체+구조 보존 신규 지식포맷)를 신설해 dense 벡터(pgvector)와
PageIndex(목차 트리 기반 탐색) 두 검색 도구의 공통 소스로 삼는 설계(§5-3·§5-4)를
실제로 구현.

### PageIndex 채택 관련 중요 발견
설계문서가 "채택 확정, 세부구현 미정"으로 남겨뒀던 부분. **`pip install pageindex`
(공식 PyPI 패키지)를 실제로 설치해보니 로컬 트리생성 코드가 아니라
`https://api.pageindex.ai`(유료 클라우드)에 원문 파일을 업로드하는 REST
클라이언트였다** — 이 프로젝트는 전 구간 airgap(런타임 외부 인터넷 완전 차단)이라
그대로 쓸 수 없었다. GitHub 원저장소(MIT 라이선스)를 직접 확인해 로컬 실행
가능한 "Self-host" 경로만 가져와 komir 안에 내장(vendoring)하고, 클라우드
업로드 클라이언트 코드는 아예 제거했다.

**airgap 안전성은 주장이 아니라 실측으로 확인**: 실제 LLM 노드요약까지 켠
end-to-end 실행 중 해당 프로세스가 맺은 모든 네트워크 연결을 추적해, 로컬
vLLM 서버 외 연결이 0건임을 확인한 뒤에야 채택을 확정했다.

### Argus 라이선스 문제와 사용자 확인
Argus는 유료 구독 서비스라, komir 자체 정책 코드(`source_policy.py`)가 기본적으로
"내부 파생 데이터베이스 구축" 목적의 재색인을 차단하도록 돼 있었다. 이 안전장치를
그대로 우회하지 않고 사용자에게 먼저 확인 — **사용자가 라이선스상 내부 파생 DB
구축이 허용됨을 확인**한 뒤, 이 작업에 한해서만(다른 호출자에는 정책이 그대로
유지된 채) 명시적으로 우회하도록 구현.

### 실행 결과(실측)

| 항목 | 수량 |
|---|---|
| 문서-OKF 총 문서 수 | **1,642건**(산출물 72 + 외부자료 4 + USGS 8 + 조달청보고서 868 + Argus 690) |
| PageIndex 트리 | **1,642건**(전체), 총 **78,646개 노드**, 실패 0건 |
| pgvector 청크(전체, `mineral_risk.doc_chunk`) | **140,031개**(산출물 1,030 + 외부자료 176 + USGS 5,647 + 조달청보고서 55,530 + Argus 77,648), 전부 실제 임베딩 확인(`count(embedding)`도 동일) |

### 처리 중 실측으로 발견·수정한 버그
| # | 내용 | 영향 |
|---|---|---|
| 1 | `PDF_MAXPAGES` 기본값(40쪽, 짧은 뉴스 PDF 기준)을 대용량 보고서에도 그대로 적용 | 226쪽짜리 USGS_2026 보고서가 40쪽까지만 추출돼 본문 82% 유실 |
| 2 | PDF 파서가 헤딩·표 구조가 이미 지워진 평문을 읽고 있었음 | 문서-OKF·PageIndex의 "구조 보존" 목적과 정면 배치(원본엔 헤딩 55개·표 187개가 있는데 산출 0개) |
| 3 | `search_nodes()`가 짧은 노드의 요약(`prefix_summary` 필드)을 검색 대상에서 누락 | 실제로 존재하는 내용도 검색 결과에 안 잡힘(QWK 검색 사례로 확인 후 수정) |
| 4 | Argus 문서-OKF의 `resource`(원본 경로) 필드가 하드코딩 실수로 690건 전부 존재하지 않는 경로를 가리킴 | 본문 추출 자체는 정상이었으나 원본 추적(provenance)이 깨져 있었음 |

전부 실제 처리 과정에서 발견해 그 자리에서 수정·검증했다(사전에 예측 못 한 문제들 — 실제로 대용량 코퍼스를 처음 돌려봐야 드러나는 종류).
