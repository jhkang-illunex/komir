# 챗봇(RAG) 아키텍처 — 요청 처리 흐름

> 대상: `inhouse/rag/ragkit/`(코어 로직) + `inhouse/services/rag_chat/`(FastAPI 서빙) +
> `inhouse/services/shared/`(공용 DB·LLM·근거 계약).
> 데이터 접근 계층(Postgres `mineral_risk`/`public` 스키마 구분, MCP 도구 8종의
> 스키마 소유권)은 이미 [`documents/meta/CHATBOT_POSTGRES_MCP_SPEC.md`](./CHATBOT_POSTGRES_MCP_SPEC.md)
> 에 상세 문서화돼 있다 — 이 문서는 그걸 대체하지 않고, **사용자 질문이 들어와서
> SSE 응답으로 나가기까지의 end-to-end 흐름**에 초점을 맞춘다. 컨테이너 배포 구조는
> [`documents/meta/CONTAINER_ARCHITECTURE.md`](./CONTAINER_ARCHITECTURE.md) 참조.
>
> 작성일: 2026-09-01. 시퀀스 다이어그램: `챗봇_시퀀스다이어그램_260901.drawio`(같은 폴더).

## 1. 개요

`rag_chat` 서비스는 핵심광물 수급위기 진단·수요예측 프로젝트의 대국민/내부용 챗봇
API다. 사용자 질문 한 건을 받아 **문서 Q&A**(komir 자체 산출물 + KOMIS 공개원천 +
비정형 보고서를 근거로 인용강제 답변 생성) 또는 **페이지 추천**(KOMIS 화면·메뉴
안내) 중 하나로 라우팅하고, 결과를 SSE(Server-Sent Events)로 스트리밍한다.
`POST /pubchat`·`POST /prichat` 두 엔드포인트가 실제 API 표면이며, 차이는 제3자
라이선스(Argus) 콘텐츠 포함 여부뿐(MCP "프로필" 축, §4 참고)이다.

## 2. 요청 처리 파이프라인

```
POST /pubchat 또는 /prichat (routers/chat.py)
  └─ _run_chat(request, profile)
       ├─ session_store.get_or_create_session(...)
       ├─ mode 결정: request.mode가 "document"/"page"면 그대로, "auto"(기본값)면
       │    app/intent.py::classify_intent(message) — LLM 1회 호출
       ├─ mode == "page"  → _run_page_recommend()  (§3 참고, 이 문서에서는 간략히만)
       └─ mode == "document" → _run_document_qa() → rag.ragkit.chatbot.chat_turn()
```

`chat_turn()`(`rag/ragkit/chatbot.py`)이 문서 Q&A 경로의 실제 코어다. 프레임워크
독립적(FastAPI/SSE 의존 없는 순수 async generator)이라 `routers/chat.py`는 이걸
SSE 프레이밍으로 감싸기만 한다(`_drain_sync`로 동기 제너레이터 브리지).

`chat_turn()` 내부 순서:

1. `get_or_create_session` → `session` 이벤트 emit
2. `list_messages`로 최근 히스토리(최대 `MAX_HISTORY_MESSAGES=12`, 6턴) 로드
3. `append_message`(user 메시지 저장)
4. **근거 조회** — `chatbot_graph.retrieve_evidence()`를 `_run_with_status()` 브리지로
   호출(별도 스레드 실행, `on_status` 콜백을 큐로 받아 SSE `status` 이벤트로 변환).
   진행 중 `status` 이벤트가 stage 1~3으로 실시간 emit됨(§5).
5. 근거 0건 → 유형8(범위 밖 질문) 사유 분류 후 기권 응답, `return`(생성 단계 건너뜀)
6. 근거 있음 → `status(4)` emit → LLM 스트리밍 생성(`OpenAICompatChat.complete_stream`
   을 `_iter_async`로 비동기화) → `delta` 이벤트 연속 emit
7. 생성 결과가 비었거나 `ABSTAIN_TEXT`와 같으면 → 유형8 사유 분류(같은 분류기 재사용)
   → 기권 처리
8. `_strip_uncited_sentences`(generate.py, 인용 없는 문장 전부 제거) → 남은 게
   없으면 기권(`abstain_reason="unknown"`)
9. 인용 스트리퍼 통과 후 `_dummy_data_notice` + `_caution_notice` + `_source_footer`를
   **코드로** 덧붙임(§5) → `delta` 이벤트로 추가 전송
10. `_multimodal_events`(인용된 근거의 마크다운 표 → `table` 이벤트, 숫자열 있으면
    차트 렌더링 → `image` 이벤트)
11. `append_message`(assistant 메시지 + citations 저장) → `done` 이벤트

## 3. 라우팅 — document vs page

`app/intent.py::classify_intent()`가 `mode="auto"`일 때만 호출되는 LLM 1회 분류기.
기준(2026-09-01 최종 확정판, `intent.py` 상단 주석에 여러 라운드 회귀수정 이력 상세
기록):

- **page**: 사용자가 원하는 게 "화면·기능의 위치" 자체이거나 화면 데이터를
  통째로 보고 싶어할 때만. ①어느 화면/메뉴로 가야 하는지 직접 묻는 질문, ②기능·설정의
  위치를 묻는 질문, ③"전체 데이터"를 통째로 요청하는 질문 — 이 세 가지뿐.
- **document**: 그 외 전부. 특정 수치·시계열 조회("니켈 가격 알려줘")도 document다
  (근거 조회 단계가 komir 자체 산출물 + KOMIS 공개원천 원자료를 직접 찾아 답하므로).

2026-09-01 이전에는 "화면 위치는 안 물어도 그 화면이 보여주는 수치 자체를 원하면
page"라는 기준이 있었다(당시 document 경로가 KOMIS 원천 수치를 못 다뤄서 대신 화면
위치라도 안내하던 우회책) — `komis_raw_lookup` MCP 도구 신설로 document 경로가 직접
답할 수 있게 되면서 이 기준을 없앴다. 분류 실패(LLM 오류) 시 안전하게 `document`로
폴백한다(문서 경로는 근거 0건이면 기권으로 끝나 오분류 비용이 더 작다는 설계 판단).

## 4. 근거 조회(retrieval) — LangGraph 오케스트레이션

`chatbot_graph.py`가 `route → retrieve → verify → (불충분하면) reformulate → retrieve
→ verify → finalize` 상태그래프를 돈다(`MAX_ATTEMPTS=2`, 최초 1회 + 재시도 1회).

- **route** (`ROUTE_PROMPT`, LLM 1회): 히스토리 기반 대용어 해소(`resolved_query`)
  + 4개 도구 중 무엇을 켤지 결정(`RetrievalRoute`):
  - `structured`: komir 자체 산출물(`latest_diagnosis`/`import_forecast`/
    `geo_index_trend`) — **5광종(CU/NI/CO/LI/REE)만** 실제로 계산돼 있어 이 5개로
    제한(인위적 화이트리스트가 아니라 데이터 자체의 한계).
  - `komis_raw`(2026-08-31 신설, 2026-09-01 전 광종 확대): KOMIS 공개원천
    (가격·교역·매장량·생산량·시장전망·수급안정·가격예측) — **5광종 제한 없음**,
    KOMIS가 다루는 광종이면 무엇이든(텅스텐·금·은 등) 조회 시도.
  - `dense`(pgvector 하이브리드 검색), `pageindex`(OKF 트리 탐색, `simple`|`agentic`
    모드) — 둘 다 비정형 보고서 대상, 광종 제한 없음.
- **retrieve** (`_retrieve_node`): route가 켠 도구들을 `ThreadPoolExecutor(4)`로
  **병렬 호출**. `komis_raw`를 켰으면 먼저(동기) `komis_resolve_mineral`로
  `komis_mineral_name`(자유형 한글) → `mineral_code`+`price_category`를 알아낸 뒤
  페이지ID를 결정적으로 매핑(`_komis_raw_page_id`)하고서야 풀에 넣는다. 도구 하나가
  실패해도(DB 미접속 등) 나머지로 부분 열화 진행 — 전체 실패가 아니다.
  실제 원격 호출은 MCP 클라이언트(`mcp_client.py`, `state["profile"]`로 public/private
  세션 선택)를 경유한다 — 도구 구현(`services/shared/retrieval/*`)과 Evidence 변환은
  서버(`mcp_server_public.py`/`_private.py`) 쪽에서 실행됨.
- **verify** (`VERIFY_PROMPT`, LLM 1회): 근거가 실제로 질문에 답하는지 확인("같은
  광종·주제"만으로는 불충분 — 지표 자체가 달라도 불충분). 근거 0건이면 LLM 호출 없이
  바로 불충분 처리.
- **reformulate**: 불충분 판정 시 검색어 재작성(한국어→영어 전문용어 보강 등) +
  `dense`/`pageindex`를 추가로 켜고(끄지 않음, 합집합) 재조회.
- **finalize**: 재시도 후에도 불충분하면 — 근거가 하나도 없으면 그대로 기권 경로로,
  근거가 있으면(지표는 다르지만 관련은 있는 경우) `retrieval_near_miss` 경고를 달아
  near-miss 제안형 답변(§5)의 재료로 남긴다.

4개 데이터원(Postgres `mineral_risk`/`public` 스키마, Vector DB, OKF/PageIndex)의
소유권·접근 계층·MCP 도구 매핑 상세는 `CHATBOT_POSTGRES_MCP_SPEC.md` §0-1/§0-1-1을
참조.

## 5. 답변 생성 — 인용 규칙과 안전장치

`CHATBOT_SYSTEM_PROMPT`(일반 문서 Q&A)와 `NEAR_MISS_SYSTEM_PROMPT`(근접매칭 제안형,
근거는 있지만 정확히 원하는 지표는 아닐 때)로 갈린다. 공통 인용강제 규칙(오직
[근거]만, 숫자·이름 날조 금지, 인용 없는 문장 금지)은 `generate.py`(비-챗봇 RAG
경로와 공유)의 원칙을 그대로 상속하되, 어투·유형별 지시(`documents/order/chatbot_rule.txt`
반영)를 얹은 별도 프롬프트 상수를 쓴다.

세 가지 **코드로 강제 부착**하는 후처리(모두 `_strip_uncited_sentences` 통과 **이후**
에 붙인다 — 인용 없는 문장으로 취급되면 스트리퍼가 지워버리기 때문):

1. **`_dummy_data_notice`**(2026-08-31 신설): 인용된 근거 중 `Evidence.caveat`가
   채워진 게 있으면(현재는 `komis_raw_lookup`이 KOMIS 실제 표본이 아닌 개발용 더미
   데이터를 인용했을 때만) 매 인용마다 경고 강제 부착 — 캐시 없음, 안전에 직결되는
   경고라 중복 노출을 감수한다.
2. **`_caution_notice`**: `structured`(특히 `latest_diagnosis`) 근거가 인용되면
   "인과관계 단정 아님" 주의 문구.
3. **`_source_footer`**: 인용된 근거의 출처 목록.

**near-miss 복수인용 함정**(2026-08-31 실사용 버그, 텅스텐 가격질문에서 재현):
인용 스트리퍼(`generate.py::CLAUSE_RE`)는 `[1][2][3]`처럼 대괄호가 개별로 붙은
형태만 매칭한다 — LLM이 `[1, 2, 3]`처럼 하나의 대괄호에 쉼표로 나열하면 문장 전체가
무인용으로 간주돼 통째로 사라진다(near-miss 제안문이 없어져 "자료가 아예 없다"는
가짜 완전기권으로 보였다). `NEAR_MISS_SYSTEM_PROMPT` 규칙5로 개별 대괄호 형식을
명시해 수정.

**유형8(범위 밖 질문) 사유 분류**(`_classify_abstain`): 근거 0건 기권과, 근거는
찾았지만 생성 LLM이 스스로 `ABSTAIN_TEXT`로 기권한 경우 둘 다에서 호출(2026-08-28
실사용 감사로 후자가 더 흔한 경로임이 밝혀져 스코프 확장). `off_topic`/
`no_data_for_period`/`ambiguous`/`retrieval_error`(도구 자체 장애, 사용자 탓 아님)
네 갈래로 분류해 사유별 안내문을 화면에 노출.

## 6. 알려진 설계 결정과 이유(2026-09-01 기준 유효한 것만)

- **5광종 화이트리스트 전면 철폐**(2026-09-01): `CHATBOT_SYSTEM_PROMPT` 옛 규칙11
  ("동·니켈·코발트·리튬·희토류 5개만 다룬다")과 `_AbstainReason.unsupported_commodity`
  를 제거했다. 사용자 정정: "5대 광종 제한은 이 프로젝트 일부(진단·예측 등 komir
  자체 산출물)에서 쓰는 제한이지 챗봇 전체는 아니다." `structured`(komir 산출물)만
  여전히 5광종인 건 데이터 자체의 한계이지 인위적 제한이 아니다.
- **`komis_raw` 전용 광종 필드 분리**(`komis_mineral_name` vs `commodity_code`):
  `structured`는 Literal 5종 고정, `komis_raw`는 자유형 한글명 — 광종 코드-한글명
  매핑은 `ai_mnrl_mst` 실조회(`komis_resolve_mineral`)로 하드코딩 딕셔너리를 대체.
- **SSE status 4단계 정수 계약**: `retrieve_evidence(on_status=...)`가 내는 문자열
  stage(routing/retrieving/verifying/reformulating)를 `_GRAPH_STAGE_TO_STATUS`로
  정수 1~3에 매핑하고, 생성 시작(stage 4)은 `chat_turn`이 직접 emit — 프론트(streamlit_demo)
  와 정수+label 계약으로 조율 완료.
- **`/chat` 하위호환 별칭 비노출**: 구현(`chat()` 함수)은 남기되 `@router.post`
  미등록 — 필요시 데코레이터만 다시 붙이면 재도입 가능.
