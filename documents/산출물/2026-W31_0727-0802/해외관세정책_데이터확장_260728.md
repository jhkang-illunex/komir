# 해외 국가 관세·정책 데이터 수집 확장 — 조사·반영 결과 (2026-07-28)

발주처 지정 수집 대상(tier1 3개국·tier2 6개국, 국가×광종×기관)에 대해 기관별
공개 데이터 경로를 전수 조사(웹 조사 3건 + 본 서버 실호출 재검증)하고,
**무키·무인 수집이 가능한 소스는 당일 수집기 구현·백필까지 완료**했다.
API 키 발급·유료 구독 등 별도 절차가 필요한 소스는 §4에, 기술적 불가와
대안은 §5에 정리한다. 모든 판정은 실제 HTTP 호출 결과 기준(문서 재인용 없음).

## 8. 키 발급 후속 반영 (2026-07-29)

사용자가 §4의 #1~#3(BPS·Census·Comtrade)을 당일 가입·발급, `.env`에 저장
(`BPS_API_KEY`·`CENSUS_API_KEY`·`COMTRADE_API_KEY`/`_2`). 실호출로 3건 모두
검증 후 아래와 같이 처리했다.

### 8-1. 미 Census — 구현 완료

`collect_intl_agency_feeds.py`에 `collect_census_us()` 추가, `trade` cron
스텝에 편입. 5광종 HS4 9종(CU 2603·7403, NI 2604·7502, CO 8105, LI 2836·2530,
REE 2805·2846) × 값·관세부담액(DUT_VAL_MO) = 18개 지표.

핵심 발견: Census timeseries API가 **`time=from YYYY-MM to YYYY-MM` range
쿼리를 지원**해 HS4 코드 1개당 API 호출 1회로 2013-01~현재 전체 이력을
받는다(월별 개별 호출 불필요 — ARCA·BPS와 달리 매우 가벼움). 드라이런 검증
(DB 미접촉, 파싱 로직만): 2,864행, 18개 지표, 2013-01~2026-05 정상.

부수 발견(정성적): REE 화합물(HS 2846)의 관세부담액 비율이 특정 월 60%대로
확인(예: 2024-02 = 관세 $565만/수입액 $899만) — 301조 추가관세가 값에
직접 반영되는 걸 실측으로 확인. CBP 직접 수집(403 차단)의 대체 목적에 정확히
부합.

### 8-2. UN Comtrade 정식 키 — 검증만 완료, 기존 수집기 교체는 후속 과제

키 자체는 정상 작동 확인(연간 조회 `C/A/HS`로 실데이터 수신). 다만 **핵심
가설(정식 키가 중국 2024-12 정지를 풀어줄 것)은 기각** — 정식 API로
reporterCode=156(중국)·202501~202512 구간을 조회해도 count=0(월간 HS 상세를
아예 미제출 상태, preview와 동일). 즉 정식 키는 rate-limit(429) 완화 효과만
있고 데이터 프론티어 자체는 바꾸지 못한다.

**재확인(같은 날 사용자 요청으로 2차 검증)**: 개별 쿼리 추측이 아니라 UN
Comtrade의 **데이터 가용성 등록부 자체**(`GET /data/v1/getDA/C/M/HS
?reporterCode=156`)를 직접 조회 — 중국 월간 HS 데이터셋 141건 중 최신
분류체계(H6)까지 포함해 **전부 2024-12에서 끝나고 2025-01 이후 등록 자체가
없음**을 확정. 연간(`C/A/HS`)도 최신이 2024년(33건)이고 2025년 연간치도
미등록 — 통상 연간은 익년 내 제출되는 관례를 감안하면 월간뿐 아니라 **전반적
보고 중단**으로 해석된다. 즉 이 결측은 특정 상품코드·API 등급의 문제가 아니라
중국이 UN 측에 어떤 형태로도 2025년 이후 무역통계를 제출하지 않고 있다는
뜻이며, 어떤 방법으로도(무키·유키 불문) 해소되지 않는다.

기존 `collect_priority_feeds.py`의 `_comtrade_fetch()`(tier1·tier3·tier4가
공유 임포트)를 이 키로 교체하면 429 재시도 대기(1.6초/콜)를 줄일 수 있으나,
**이미 검증된 챔피언 파이프라인의 공유 헬퍼를 건드리는 변경**이라 이번
세션에서는 반영하지 않았다 — 회귀 없음을 확인할 재검정까지 포함해 별도
사이클로 진행 권고.

### 8-3. 인니 BPS — 발급됐으나 미승인, 보류

키 형식(32자리 hex, 공백 없음) 확인, 공식 문서의 파라미터명·trailing slash까지
전부 대조했음에도 `dataexim`은 물론 가장 기본적인 `domain` 조회 엔드포인트까지
**전부 "키를 다시 확인하세요" 거부** — 파라미터 문제가 아니라 **BPS 쪽 앱
상태(활성화 대기 등)로 추정**. 사용자에게 BPS 개발자 포털에서 앱 상태 확인을
요청함. 활성화 확인되면 `collect_intl_agency_feeds.py`에 인니 니켈 HS 수집
함수 추가 예정(파라미터 구조는 이미 문서로 확보 — 코드 자체는 짧음).

### 8-4. 중국 GACC 상세(stats.customs.gov.cn) — headless 스크래퍼 실제 시도, 실패 확정

사용자 요청으로 "정말 되는지" 실제 검증(Playwright, `mineral_supply_risk`
바깥 스크래치패드에서 진행 — 결론이 부정적이라 저장소 미커밋). 순수 HTTP
차단(412+JSL, 07-28 실측)을 headless 브라우저로 우회할 수 있는지 5단계로
시도했고, **전부 실패**했다.

| # | 시도 | 방법 | 결과 |
|---|---|---|---|
| 1 | 기본 Playwright | headless Chromium, 실제 UA, `networkidle` 대기 | 412 → 챌린지 JS 로드(200, 쿠키 4개 발급: `AV7KYchI7HHaS/T`·`__jsluid_h`·`SF_cookie_251`) → 콘텐츠는 빈 페이지(`<html><head></head><body></body></html>`) |
| 2 | 응답 이벤트 추적 + 명시적 재로드 | `page.reload()`로 챌린지 후 재요청 명시 유도 | 자동 재탐색이 실제로 일어남을 확인 — 단 최종 응답이 **400**(412도 200도 아닌 새 상태) |
| 3 | `navigator.webdriver` 등 개별 지문 은폐 | init script로 webdriver/languages/plugins/chrome.runtime/permissions.query 패치 + `--disable-blink-features=AutomationControlled` | webdriver 은폐 확인(`None`)됐으나 **412→200→400 결과 완전 동일**(바이트 단위로 동일) |
| 4 | `playwright-stealth`(업계 표준 종합 은폐 라이브러리, v2.0.3) | 라이브러리 기본 evasion 세트 전체 적용 | webdriver=False 확인됐으나 **역시 412→200→400 동일** — 개별 패치보다 포괄적인 도구조차 통과 못 함 |
| 5 | HTTPS 경로(인증서 검증 무시) | `ignore_https_errors=True`로 `https://` 접근 | HTTP와 **완전히 다른 인프라**로 라우팅됨(Yunjiasu/云加速 CDN — 응답에 `browser.jpeg`·`node-yunaq.jpeg`·`line.jpeg`·`origin.jpeg` 진단 이미지 포함된 요청경로 시각화 오류 페이지) → **504 오리진 서버 무응답**. 07-28 실측한 "self-signed 인증서 체인 오류"의 실체가 이 CDN 구성 문제였음이 드러남 |

400 응답 헤더 추가 확인: `x-via-jsl: c84a5e4,-`(JSL 프록시가 요청을 실제로
처리했음을 의미)·`cache-control: no-store`·본문 없음 — 진단 메시지 없이
차단.

**결론**: 챌린지 스크립트 자체가 VM 바이트코드로 난독화된 상용 봇탐지 제품
(가속락/JSL로 추정)이라 수동 역공학은 비현실적이고, 지문 스푸핑 수준의
대응(개별 패치·표준 라이브러리 둘 다)으로는 뚫리지 않는 것이 재현
확인됐다. HTTP 경로는 400으로, HTTPS 경로는 504로 — **서로 다른 이유로
막힌 두 경로 모두 막다른 길**이다. §4 #6의 판정을 "(a) 취약"에서
**"(a) 불가"로 하향 조정**한다 — 이 방향은 추가 투자할수록 손실만 커지는
방향이므로 재시도 금지, 유일한 실행 경로는 §4 #6-(b) 상용 벤더 구독뿐.
