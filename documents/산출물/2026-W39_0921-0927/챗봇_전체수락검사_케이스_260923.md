# 챗봇 전체 수락 검사 케이스 — 2026-09-23

작성: Astra. 범위: 현재 가동 중인 챗봇과 문서 색인 경로. **48개 케이스 정의 완료이며, 이 문서는 실행 성공 보고서가 아니다.** 전체 데이터의 모든 행을 48개로 검증한다는 뜻이 아니라, 가동 데이터 종류·질문 유형·모듈 경계의 대표 계약을 검증한다.

기계 판독 정의는 `inhouse/rag_chat/tests/chatbot_acceptance_cases.yml`이다. YAML 1.2에서 유효한 JSON 문법으로 작성했다. 각 케이스에 질문, 예상 action/소스, 판정, SSE 계약, 세부 검사, 대상 모듈, 데이터 사전조건이 들어 있다.

## 1. 구성과 판정 원칙

| 실행층 | 개수 | 검사 |
|---|---:|---|
| live | 32 | 실제 /pubchat 자연어 요청. AC22는 같은 세션 후속 요청까지 2턴 |
| module | 10 | 고정 입력·가짜 외부 응답으로 계산·분기·SSE 생성 계약 검증 |
| integration | 6 | 실제 문서·DB 읽기 전용 조회로 포맷·색인·검색 연결 검증 |
| 합계 | 48 | 전체 결과와 개별 결과를 모두 기록 |

결과는 PASS / FAIL / BLOCKED_DATA / BLOCKED_ENV / NOT_RUN으로 나눈다. 정상 기권은 기대 계약이 기권이고 정확한 사유·빈 인용·빈 표/차트를 만족하면 PASS다. 타임아웃, 서버 오류, 생성 오류는 정상 기권으로 합격시킬 수 없다. 성공을 요구하는 케이스에서 자료를 사전 확보하지 못했다면 BLOCKED_DATA이며 성공률 분모에서 조용히 제외하지 않는다.

실행 전에 독립 SQL·원문 확인으로 데이터 사전조건을 확정하고 결과 파일에 저장한다. 응답이 실패한 뒤 기대값을 “답 또는 기권 모두 허용”으로 바꾸지 않는다. 더미 자료가 허용된 시연 케이스는 결과에 이를 표시하며 실제 통계 정확성 검증으로 주장하지 않는다.

새 HITL은 `trade.indicator`의 누락 슬롯에 한정한다. 기존 광산 소재지/소유 구분 clarification은 별도 기존 계약으로 유지한다. 모든 일반 질문에 무역 HITL을 확대하지 않는다.

`expected_actions`는 기본적으로 요구 action의 집합이다. 한 질문이 같은 action으로 여러 requirement를 만들 수 있으므로 중복 개수는 해당 케이스의 checks에서 별도로 판정한다. AC33의 `actions_match:any`는 진단 순위 또는 시계열 어느 분류이든 같은 미연결 경계를 검증한다.

`expected_sources`의 Vector/PageIndex/OKF는 논리적 소스 이름이다. 실제 citations.source 문자열과 그대로 비교하지 않는다. 실제 파일 경로·evidence kind·retrieval_sources·도구 호출을 함께 확인한다. 검색된 모든 소스가 최종 인용으로 남아야 하는 것은 아니다.

## 3. 공통 SSE 계약

- terminal: HTTP 200, 정상 JSON SSE, 요청별 done=true 정확히 1개, session_id 보존.
- grounded_answer: 답변 본문과 유효 인용, 기대 action/원천 연결, 표·차트의 헤더·단위·data_ref 정합.
- clean_abstention: abstained=true, 사전 기대 사유, 설명 본문, 인용·표·차트 없음.
- clarification: needs_clarification=true, trade.indicator와 누락 슬롯 명시, 계산 결과 없음.
- page: done.mode=page와 기대 recommendations.page_id. 메뉴 안내에는 일반 수치 답변의 citations 필수 조건을 적용하지 않는다.
- not_applicable: HTTP 없는 모듈/통합 검사. SSE 성공으로 집계하지 않는다.

현재 성공 응답의 `retrieval_sources`를 검사하되 사전 차단 기권 응답에 없는 필드를 임의로 필수화하지 않는다. 아직 구현·합의되지 않은 별도 “근거 없음” 플래그도 현재 계약에 추가하지 않는다.

표 검사는 열 이름으로 수행한다. 순번이 제거된 현 UI에서 row[0]이 순위라는 과거 검사를 재사용하면 안 된다. 숫자는 원천 SQL/원문으로 계산하며 고정 과거 가격이나 고정 줄번호를 정답으로 삼지 않는다.

## 4. 실행기 구현

`inhouse/rag_chat/tests/run_acceptance_suite.py`를 추가해 YAML의 케이스 ID별 실행을 구현했다. 기본값은 module·integration이며, live는 `--layer live` 또는 `--case`로 명시 실행한다. `--case`를 지정하면 layer 기본값을 재정의한다. 결과는 `documents/산출물/acceptance_results/*.json`과 케이스별 즉시 기록 JSONL에 저장한다.

- live: SSE의 단일 `done`·세션 보존·done 뒤 이벤트 금지, action·출처 인용, 정상 기권 사유, 비어 있지 않은 답변/기권/HITL 설명, HITL 누락 슬롯, 메뉴 page_id와 public `login_required` 차단을 검사한다. terminal 계약 위반은 데이터 차단보다 먼저 FAIL이다. `expected_message_key`가 있으면 terminal payload와 대조한다.
- AC22는 첫 턴 clarification과 같은 session_id의 보충 턴 grounded answer를 각각 검사한다. 그러나 첫 슬롯 보존·후속 광종/기간/지표 변경 거절과 독립 계산값 대조가 아직 없으므로 현재는 PASS가 아닌 FAIL이다.
- module: YAML의 `unit_tests`를 개별 `unittest`로 실행한다. `additional_checks_required`가 하나라도 남은 케이스는 unit test 성공만으로 PASS가 될 수 없으며 FAIL로 기록한다.
- integration: PDF/HWP/XLSX 표본은 원본·OKF·PageIndex tree·읽기 전용 pgvector를 실제로 대조한다. dense는 fallback 없이 실제 top-10을 실행하고 `doc_id`·본문·`source_path`를 인덱서 계약으로 비교한다. HWP는 ODT XML 표 셀의 두 사실, Excel은 고정 시트·헤더·파일명 연도·단위·두 값을 원본에서 확인한다. 불일치·검색 실패는 FAIL이다.
- `test_acceptance_suite_runner.py`: 48개 고유 ID·3개 계층·SSE 정상/부정 fixture·명시 case layer 재정의·AC22 2턴 세션을 회귀 검사한다.

통합 핸들러의 YAML 목표 계약:
1. `document_pdf`: PDF 원본→OKF→트리→청크와 실제 검색·본문 대조.
2. `document_hwp`: HWP/HWPX 원본과 추출 본문 대조.
3. `document_excel`: XLS/XLSX 원본의 시트/헤더/값 보존 대조.
4. `vector_retrieval`: 실제 dense_pg 호출·기대 doc_id·청크와 임베딩 연결 대조.
5. `pageindex_lookup`: 실제 PageIndex 노드 검색, 줄 범위의 OKF 본문 대조.
6. `ocr_three_documents`: 11.27/12.18/주간_080225 각 문서의 원문 구간·추출 본문·노드·청크 회귀.

현재 실행기는 고정 fixture의 resource/doc_id/okf_path, 원문 사실, fixture·현재 OKF·Tree 저장 hash, 독립적으로 계산한 본문 줄 범위, 실제 PageIndex `search_nodes()`·`read_node_text()`, pgvector의 최신 청크 본문을 대조한다. Tree의 `doc_<24자>`와 vector의 `doc_` 제거 후 16자 ID는 공식 인덱서 규칙으로 연결하고 `source_path`도 함께 확인한다. 고정 사실을 만족하지 않는 검색 결과는 PASS로 바꾸지 않는다.

module층의 `unit_tests`는 기존 unittest 모듈/메서드로 연결하되, 기존 테스트가 checks 전체를 보장하는지는 따로 확인한다. `additional_checks_required`가 있으면 해당 신규 검사를 구현하기 전에는 그 케이스 전체 PASS를 선언하지 않는다.

라이브는 기본 동시성 1, 케이스별 180초 상한, 자동 재시도 0으로 시작한다. 재실행은 실패 원인 기록 후 별도 실행 ID를 남긴다. 32개 케이스, AC22 후속 1턴이 모두 제한시간을 사용하면 HTTP 대기만 최대 99분이다. 이는 예상 실행시간이 아닌 상한이며 사전조건 검사와 모듈/통합 시간은 별도다. 실행기는 각 케이스가 끝나는 즉시 JSONL에 결과와 raw SSE event를 저장해 중단 후에도 이미 얻은 증거를 보존한다.

결과 레코드 확장 목표(아래 항목 전부가 runner JSON에 구현된 것은 아니며, 이번 실행의 Git·코드 해시는 별도 `final_verification.json`에 보존): run_id, case_id, layer, status, expected/actual_outcome, failed_checks, elapsed_seconds, git SHA/dirty 여부, 컨테이너 이미지 ID, endpoint/profile, model 식별자, 원천 스냅샷 시각, preflight 자료 경로, SSE 원본 경로, 인용 doc_id/기간, module_test 결과. 연결 문자열·API 키는 저장하지 않는다.

### Round 2 P1 제한 사항

가격·교역·자원·보고서 답변(AC01 등)의 수치, 표, 단위, 실제 관측기간을 독립 원천과 대조하는 검사가 아직 없다. 따라서 page 안내 이외의 정상 답변은 기본 SSE 계약을 만족해도 PASS로 기록하지 않고 FAIL로 남긴다. `source_unavailable`은 같은 실행에서 저장한 독립 사전조건 증거가 있을 때만 BLOCKED_DATA가 될 수 있으며, 현재 YAML 케이스에는 그 증거 필드가 없다.

Round 2는 P1 범위만 반영했다. 실제 dense 검색의 의미 적합성, 모든 보고서 본문 구간의 문장 단위 대조, 수치 재계산 fixture 확대와 같은 P2 항목은 이 실행기에서 아직 구현하지 않았으며 제한 사항으로만 기록한다.

### Round 4 고정 입력 경계 검사

AC42는 실제 `_retrieve_node`에서 RDB·dense·PageIndex 세 조회가 Barrier(3)를 통과하고 각각 정확히 1회 호출되는지, PageIndex 예외에도 RDB와 dense 근거가 보존되는지 확인한다. AC44는 92·93·364·365·1095·1096일 경계와 가격 평균·금액 합계를 고정 입력으로 확인한다. AC47은 TSI·RCA·TII·증감률·특정국 의존도의 수치 예와 0 분모, 무역 HITL의 누락/완료 슬롯을 확인한다. 이 세 검사는 실행기 결과의 `required_checks`에 ID와 unittest target을 남긴다.

### Round 5 통합 어댑터 연결

`acceptance_integrations.py`를 runner의 AC28~30·AC39~41 dispatcher에 연결했다. PDF/HWP/Excel은 고정 원본 존재, 대응 Tree, OKF의 고정 사실, 실제 `dense_search_pg` 후보 본문·source/doc 연결, 같은 `doc_id`의 embedding chunk를 순서대로 확인한다. AC40은 `search_nodes()`와 `read_node_text()`의 실제 본문, AC41은 3개 고정 OKF 각각의 node text와 같은 `doc_id` chunk를 확인한다. 결과 detail의 `required_checks`에 각 단계 PASS/FAIL/BLOCKED 상태를 남긴다.

### Cycle2 Round4 통합 고정 표본

당시 통합 어댑터는 Tree ID를 pgvector ID와 직접 비교했다. 후속 감사에서 이 비교가 공식 ID 변환 규칙을 누락한 검사 결함임을 확인하여 수정했다. 현재는 Tree의 `resource`, `doc_id`, `okf_path`와 공식 변환한 vector ID·`source_path`·본문 사실을 함께 비교한다. AC39는 `dense_search_pg(..., k=10, _allow_fallback=False)`만 허용한다. AC28의 기존 dense top-10 불일치 fixture는 실행 후 변경하지 않았고 계속 FAIL로 남긴다.

AC40과 AC41은 fixture에 고정한 doc/resource, OKF 본문 SHA-256, **프론트매터를 뺀 본문 기준** 줄 범위와 사실을 먼저 확인한다. 이어 실제 `search_nodes(doc=...)`와 `read_node_text()`에서 같은 사실을 확인하고, 같은 doc_id의 embedding `doc_chunk`도 확인한다. AC41은 세 OCR 문서를 모두 시도해 한 문서의 실패가 나머지 두 문서 검사를 생략시키지 않는다.

AC29는 `hwp5odt` 결과의 `content.xml`에서 두 니켈 사실을, AC30은 XLSX `산출결과` 시트의 헤더, 파일명 연도(2025), `광석 생산량(kwmt)`, 값 41875 및 303.7481341598289를 대조한다. 원본 파서/DB/임베딩 호출 자체가 불가능한 경우에만 해당 오류를 근거와 함께 BLOCKED로 기록하며, 원본·색인·검색 불일치는 FAIL이다.

당시 6건 FAIL에는 검사 결함과 실제 검색 실패가 섞여 있었다. 특히 AC41의 full Tree ID 조회 0건을 청크 부재로 해석한 것은 잘못이었다. 실제 공식 vector ID로는 1·2·23개 청크가 존재한다. [이전 독립 실행](acceptance_cycle3/komir-astra-cycle2-round4/chatbot_acceptance_20260923_034126.json)을 영속 보존했고, 후속 수정과 같은 고정 입력 재검증은 아래 최종 보고에 기록했다.


### 후속 반복 최종 검증

Astra 조정·독립 검증, `gpt-5.6-sol` 통합 검사 구현, `gpt-5.6-terra` 추출 메타데이터 수정으로 진행했다. [최종 보고](챗봇_후속반복감사_최종결과_260923.md)와 [메타데이터 원인·후속 처리](챗봇_추출메타데이터_감사_260923.md)를 함께 참고한다.

- acceptance 회귀 33건, ingest 회귀 46건, module 10건 통과. 서로 다른 검증 계층의 숫자를 전체 질의 성공 건수로 합산하지 않는다.
- 고정 통합 6건은 AC41만 PASS이며 나머지 5건은 FAIL이다. 실제 원본·DB·모델이 있어 이번 실행에 BLOCKED는 없다.
- 정상 대조군에서 19개 오류 변형과 HWP 다른 광종 행·Excel 열 교환·필수 검사 누락/중복을 별도로 확인했다.
- `detail.required_checks`는 사전 정의 ID별 정확히 1개이며, 실행하지 못한 검사에는 SKIPPED와 이유를 기록한다. SKIPPED를 전체 PASS로 처리하지 않는다.
- 기존 fixture의 모든 값(질의·사실·기존 hash·범위 포함)은 변경하지 않았다. 기존 intent/action/router 3개 핵심 파일의 SHA-256도 작업 전후 동일하다.
- live 32건 전체와 서비스 재배포는 수행하지 않았다. 로컬 코드 검증을 배포 완료 또는 전체 챗봇 수락 완료로 표현하지 않는다.
