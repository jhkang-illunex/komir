# report_gen 분석요약(AI 통계분석 요약) 작성 원칙 및 검증 방식

> 2026-09-10 작성. report_gen 10페이지(광물자원가격 4종·광물전망지표 3종·
> 수급지도/광물지도 3종) 분석요약 기능이 "무엇을 근거로 어떻게 문장을
> 만들고, 그게 맞는지 어떻게 확인하는가"를 한 문서로 정리한다. 코드
> 상세는 `inhouse/report_gen/app/analysis/`, 변경 이력은
> `documents/meta/WORKLOG.md`가 정본이며 이 문서는 그 위에 얹은 원칙
> 요약이다.

## 0. 한 줄 요약

**분석요약 문장은 전부 미리 계산된 사실(evidence)에서만 나온다. 문장을
매끄럽게 다듬는 건 LLM의 역할이지만, 숫자·사실·꼭 필요한 서술 틀을
지키는 건 코드(검증기)의 역할이다 — 둘 중 하나가 실패해도 사용자에게는
항상 "검증된 정확한 문장"만 나간다.**

---

## 1. 보고서 작성 원칙

### 1.1 근거 기반 작성 — 모든 문장은 evidence에서 나온다

- 계산 단계(`komir_summary.py`·`indicator_summary.py`·`additional_summary.py`)가
  KOMIS 원본 응답을 파싱해 숫자·날짜·순위 등을 전부 먼저 확정한다. 이
  단계에서 각 사실은 `EvidenceClaim(id, section, fact, required)` 하나로
  묶인다 — `id`는 그 사실의 고유 이름(예: `latest_score_change`,
  `korea_route_rank`), `section`은 이 사실이 들어갈 절(`core_diagnosis`/
  `major_changes`/`current_position`), `fact`는 이미 완성된 한국어
  문장이다.
- **텍스트 생성 단계(LLM이든 규칙 기반이든)는 이 `fact` 문자열들을
  연결·재배열할 뿐, 새 숫자·날짜·사실을 만들어내지 않는다.** LLM에게
  보내는 프롬프트도 "근거를 그대로 옮긴다"·"새 수치를 지어내지 않는다"를
  페이지마다 반복해서 못박는다.
- 이 원칙 덕분에 "LLM이 헛소리를 했다"는 상황 자체가 구조적으로 나오기
  어렵다 — LLM이 할 수 있는 일은 이미 검증된 문장들을 자연스럽게 잇는
  것뿐이다.

### 1.2 이중 경로 — 규칙 기반이 항상 정답, LLM은 선택적 다듬기

- `calculate_*_summary()` 계산기가 만든 `EvidenceClaim` 목록은 그
  자체로 완결된 보고서다(규칙 기반 경로) — 각 `fact` 문자열을 그대로
  이어 붙이면 사실관계가 100% 보장된 문장이 나온다.
- LLM 정제는 이 위에 얹는 **선택적** 레이어다: 같은 `fact`들을 입력받아
  "-며"·"-고"·"-지만" 같은 자연스러운 접속 표현으로 이어 쓰거나,
  중복되는 주어·종결어를 줄인다. 성공하면 `llm_refined=True`로 표시된다.
- LLM 호출이 실패하거나(연결 오류·타임아웃), 출력이 검증(§2.6)을 통과
  못 하면 **자동으로 규칙 기반 문장으로 되돌아간다**(`llm_refined=False`).
  사용자에게 가는 응답은 이 두 경로 중 하나일 뿐, "검증 안 된 텍스트"가
  나가는 경로는 없다.
- 이번 세션에서 실제로 컨테이너의 LLM 접속 설정이 하루 종일 깨져 있던
  적이 있었는데(§2.7 배포 검증에서 발견), 그동안도 서비스는 전부
  규칙 기반 경로로 정확한 문장을 계속 서빙했다 — 이 이중 경로 설계가
  실전에서 그대로 작동한 사례다.

### 1.3 구조화된 계약 — 3섹션 + evidence_ids 인용

- 모든 페이지의 서사는 `core_diagnosis`(핵심 진단) / `major_changes`
  (주요 변화) / `current_position`(현재 위치) 3개 절로 고정된다
  (`SummaryNarrative` 모델). 절마다 허용 문장 수(최소~최대)가 페이지별로
  정해져 있고(`output_contract.section_sentence_ranges`, DB
  `ai_cfg.cfg_prompt` + 코드 기본값), 이 범위를 벗어나면 검증 실패다.
- 각 문장(`SummarySentence`)은 자신이 쓴 근거의 `evidence_ids`를 함께
  들고 있어야 한다. 검증기(`_validate_llm_summary`, §2.6)가 아래를
  전부 교차 확인한다:
  - 존재하지 않는 evidence_id를 인용하지 않았는가
  - 근거를 다른 절에서 쓰지 않았는가(예: major_changes용 근거를
    current_position에서 인용)
  - 문장에 쓰인 숫자·단계명이 그 근거의 원문에 있는 것만인가(근거 밖
    숫자·등급명 신규 사용 금지)
  - 필수(`required=True`) 근거를 하나도 빠뜨리지 않았는가, 같은 근거를
    두 번 이상 쓰지 않았는가
- 이 계약 덕분에 "LLM이 근거에 없는 이야기를 섞어 쓰는" 사고가 나면
  통과 자체가 안 되고 자동으로 규칙 기반으로 넘어간다.

### 1.4 언어·표현 원칙

- **격식체 통일**: 모든 문장은 `-습니다`/`-입니다`/`-로 나타났습니다`로
  끝난다.
- **날짜 서식 통일**(2026-09-10 발주처 피드백[8]): 일자는
  `YYYY년 M월 D일`, 월만 있는 값은 `YYYY년 M월`로 전 페이지 통일한다
  — `2026-08-25`·`2026-08` 같은 원형 ISO 표기를 본문에 남기지 않는다.
- **인과관계 단정 금지**: "원인"·"요인으로"·"~함에 따라"·"추세" 같은
  근거 없는 인과·추세 단정 표현은 코드 차원에서 아예 못 쓰게 막는다
  (`_FORBIDDEN_SUMMARY_TERMS`, §2.6). 숫자로 드러난 사실만 말하고,
  "왜 그런지"는 추정하지 않는다.
- **없는 데이터는 없다고 한다**: 계산이 불가능한 지표는 "~데이터가
  부족하다"는 식으로 지어내지 않고, 아예 그 문장을 만들지 않거나
  (`omitted_indicators`에 사유 기록), 데이터 소스 자체가 항상 비어
  있음이 확인된 경우(예: 세계수급비율 — KOMIS 원본 응답의 세계
  수요-공급 배열이 항상 빈 값)엔 그 요인 자체를 언급하지 않는다.
- **반복 금지**: 같은 수치·판단을 다른 섹션에서 두 번 말하지 않는다.
- **"그대로 옮긴다" 원칙과 그 한계**: 문장 연결·조사·어순은 자연스럽게
  다듬을 수 있지만, 이미 완성된 서술 틀(예: 점수-위험 반비례 설명,
  "대한민국이 포함된 교역 루트는 …로 확인됩니다" 같은 고정 프레임)은
  그대로 유지해야 한다. 이 경계가 프롬프트 지시만으로는 100% 안
  지켜질 수 있다는 게 이번 세션에서 반복 확인된 사실이라(§2.6),
  중요한 서술 틀은 검증기에도 별도로 못박아 둔다.

### 1.5 페이지별 특수 규칙과 렌더링 단계 처리

- 10개 page_id마다(광물자원가격 4종, 광물전망지표 3종, 수급지도/
  광물지도 3종) 고유한 서술 순서·어투·생략 규칙이 있고, 이건 JSON
  계약이 아니라 `resources/prompts/*.md` 파일에 페이지별로 따로
  적혀 있다(예: `price_summary.md`, `market_summary.md`).
- JSON 계약(`SummaryNarrative`)은 3섹션 고정이라, 4번째 절이 필요한
  경우(예: map_global "한국 관련 루트", map_mineral "주요 변화")는
  스키마를 건드리지 않고 **렌더링 단계**(`report_render.py`)에서만
  특정 evidence_id를 골라 별도 markdown 절로 분리한다. 반대로 노이즈성
  절(예: map_global "기간 변화", map_mineral "집중도 변화")은 계산·
  검증 레이어는 그대로 두고 렌더링에서만 절 자체를 건너뛴다. 계산
  로직은 항상 "값이 있을 때만" 원칙을 지키므로, 근거 자체가 없으면
  이 분리·생략도 자연히 따라간다.

## 2. 검증 방식

작은 문구 하나를 고치더라도 아래 단계를 전부(또는 해당하는 만큼)
거친 뒤에야 배포한다. 단계가 뒤로 갈수록 "실제 사용자가 보는 화면"에
가까워진다.

### 2.1 정적 검증 — `pyflakes`
문법 오류·미사용 import 등을 코드 작성 직후 바로 잡는다. 기존에
이미 있던 재수출(re-export)성 미사용 import 노이즈는 구분해서
"새로 생긴 경고인지"만 확인한다.

### 2.2 단위 테스트 — `python3 -m unittest discover -s tests`(14종)
`tests/test_report_contract.py`가 HTTP 계약(10개 라우트가 markdown
형식을 유지하는지), LLM 성공/실패 시 폴백 동작, 프롬프트 reload
동작, 인디케이터 방향·절 구성 등을 고정 값으로 검증한다(pinned
test). 문장 형태를 바꾸는 변경은 이 pinned 값도 같이 갱신한다.

### 2.3 실데이터 회귀 — 395콤보 스모크 테스트
`scripts/komis_dump_smoke_test.py`가 `income_data/komis/`의 실
KOMIS 덤프(8개 page_id, 395개 조합)로 `AnalysisSummaryService
(None, llm=None)`(규칙 기반 경로만)를 전수 실행하고, 사전에 계산한
기대값과 자동 대조한다. LLM 정제는 이 범위 밖이라 별도로(§2.5)
검증한다. 매 변경마다 `ok=395, no_data=0, internal_error=0,
mismatches=0`을 확인한다.

### 2.4 직접 렌더링 검증
스모크 테스트가 못 잡는 "이 특정 케이스에서 문장이 정확히 이렇게
나오는가"는 Python으로 직접 `AnalysisSummaryRequest`를 만들어
`service.analyze()` → `render_markdown_report()`를 호출해 눈으로
대조한다. 극값(증가국 0곳/감소국 0곳, 현재가=최고가 등)·데이터
결측·병합-분리 분기 등 스모크 테스트의 1회성 샘플로는 안 걸리는
경계 조건을 이렇게 짚는다.

### 2.5 실LLM 재검증 — "규칙 기반과 겉보기엔 구분이 안 된다"는 함정
LLM 정제 경로는 규칙 기반과 같은 사실관계를 문장화하므로, curl로
받은 텍스트가 그럴듯하다는 것만으로는 LLM 경로가 실제로 탔는지
알 수 없다. 응답의 `llm_refined` 필드(또는 서버 로그의
`llm_refined=True/False`)를 반드시 같이 확인한다. 또한 LLM은
`temperature=0`이어도 매 호출의 전체 맥락에 따라 확률적으로 다른
표현을 낼 수 있어, 같은 요청을 3~10회 반복 호출해 표현이 매번
일관되게 올바른지 스트레스 테스트한다 — 이번 세션에서 "동작할
때마다 나왔다 안 나왔다 랜덤"이라는 사용자 관찰이 실제로 이 확률적
특성 때문이었음을 확인했다.

### 2.6 구조적 백스톱 — 프롬프트 지시만으론 못 막는 것을 검증기로 막는다
"이 문구는 절대 지우면 안 된다"·"이 표현은 절대 쓰면 안 된다"는
지시를 프롬프트(.md)에만 적어두면, LLM이 전체 문장을 자연스럽게
다듬는 과정에서 확률적으로 그 지시를 어길 수 있다(이번 세션에서
3회 실측: 점수-위험 반비례 설명 문장 소실, "같은 최근" 지시어 재발,
"한국 관련 루트" 서술 틀 소실). 이런 경우 프롬프트 수정만으로
끝내지 않고 `_validate_llm_summary`(출력 검증기)에 구조적 안전장치를
추가한다:
- **금지어 차단**(`_FORBIDDEN_SUMMARY_TERMS`): 특정 표현 자체가
  본문에 나오면 무조건 검증 실패 → 규칙 기반 폴백(예: "추세",
  "같은 최근").
- **타겟 content-presence 검증**: 특정 evidence_id를 인용한 문장이라면,
  그 근거의 fact에 있는 핵심 구절이 출력 문장에도 그대로 있어야
  한다는 걸 개별적으로 확인(예: "점수가 낮을수록 위험이 커지는" 구절,
  "대한민국이 포함된 교역 루트는" 접두어).
검증에 걸리면 그 즉시 규칙 기반 폴백으로 넘어가므로, 사용자에게는
항상 안전한 문장만 나간다 — "프롬프트로 지시 + 검증기로 강제"를
한 쌍으로 취급하는 게 이번 세션에서 확립된 원칙이다.

### 2.7 배포 검증 — 로컬 검증과 실제 서빙 환경의 차이
로컬(호스트)에서 통과한 검증이 배포된 컨테이너에서도 그대로
맞는지 별도로 확인한다:
1. `docker build`로 이미지 재빌드
2. 기존 테스트 컨테이너 교체(`docker run` — 특히 `LLM_BASE_URL`처럼
   컨테이너 전용 오버라이드가 호스트 값과 다른 환경변수는 빠뜨리지
   않는다. 이번 세션에 이걸 빠뜨려 하루 종일 LLM 정제가 조용히
   전부 실패한 사고가 실제로 있었다 — "겉보기엔 정상"이라 §2.5의
   `llm_refined` 확인 없이는 못 잡는 유형이다)
3. `python3 -m app.analysis.seed_prompts` 재실행(프롬프트는 DB
   `ai_cfg.cfg_prompt`에서 서빙되므로, 파일만 고치고 이 단계를
   빠뜨리면 배포에 반영되지 않는다)
4. `POST /admin/prompts/reload`
5. 배포된 컨테이너에 실제 `curl`로 최종 확인(가능하면 실LLM 경로까지)

프롬프트(.md) 파일만 바꾼 경우엔 3~5단계만으로 충분하고 이미지
재빌드는 필요 없다 — 코드(.py)가 바뀐 경우에만 1~2단계부터 다시
한다.

### 2.8 변경 이력 기록 — `documents/meta/WORKLOG.md`
모든 변경은 배포 직후 WORKLOG에 "무엇을·왜·어떻게 검증했는지"를
남긴다. 재현 가능한 예시 문장·정확한 수치·커밋 해시를 같이 적어
두면, 나중에 같은 종류의 문제가 재발했을 때(실제로 이번 세션에서
여러 번 있었다) 과거 기록을 근거로 원인을 빠르게 좁힐 수 있다.

## 3. 요약 — 두 축으로 기억하기

|---|---|---|
