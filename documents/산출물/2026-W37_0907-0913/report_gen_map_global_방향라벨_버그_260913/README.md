# v10.pptx map_global(글로벌수급지도) 2개 슬라이드 데이터 오류 발견·수정 (2026-09-13)

> 사용자 제보: "글로벌 수급지도 리튬 2026년에서 교역 루트가 좀 이상한데요?"
> → "교역루트 1등이 호주 중국은 수출인 경우인데 슬라이드 17은 수입 이잖아요.
> 옵션에 맞게 데이터 처리 및 표시하는 부분에 오류가 있는것 같아요"

report_gen API 코드 자체의 버그가 아니라(아래 "결론" 참고), v10.pptx
map_global 슬라이드 2개가 **캡션에 적힌 조회 옵션과 실제 사용된 원본
데이터가 어긋나 있던** 문제였다. 슬라이드 16(0-idx, PPT 표시상 17번째)
과 17(0-idx, PPT 표시 18번째) 둘 다에서 서로 다른 종류의 라벨링 오류를
발견·수정했다.

## KOMIS 수입/수출 탭 코드 확인

`/Komis/MnrlMap/Nation` 페이지 HTML을 직접 열어 확인(실측):

```html
<a ... data-im="I" onClick="gotoImxprtMenu('I', this)">수입</a>
<a ... data-im="O" onClick="gotoImxprtMenu('O', this)">수출</a>
```

`srchImxprtSeCd`는 `I`(수입 탭)·`O`(수출 탭) 두 값을 받는다(`E`가 아님 —
직접 실측으로 확정, 기존 문서엔 이 매핑이 없었다). 같은 광종·기간이라도
두 탭은 **서로 다른(더 크게는 KOMIS 미러통계 방식이 달라) 데이터셋**을
반환한다(실측: 동 2025년, I탭 1위 칠레→미국 $6.09B vs O탭 1위 칠레→중국
$23.26B — 완전히 다른 순위).

## 슬라이드16(리튬 baseline) — 캡션은 "수입"인데 실제 데이터는 "수출" 패턴

라이브로 리튬(MNRL0001) 2026년을 I탭·O탭 둘 다 조회해 비교:

| | I탭(수입) — 방금 재조회 | O탭(수출) — 방금 재조회 | 구버전 슬라이드16 |
|---|---|---|---|
| 세계 교역 총액 | 1.73억 달러 | 12.41억 달러 | **1,073.71억 달러** |
| 1위 루트 | 호주→인도네시아 | **호주→중국** | **호주→중국** |
| 2위 루트 | 칠레→독일 | 아르헨티나→중국 | 칠레→중국 |

구버전 슬라이드16의 1위 루트("호주→중국")는 O탭(수출) 패턴과 일치하고
I탭(수입) 패턴과는 다르다 — 캡션엔 "수입"이라고 적혀 있는데 실제 순위
패턴은 "수출" 쪽이었다는 사용자 지적이 정확했다. (금액 자체($107.4B)는
지금 재조회한 O탭 값($1.24B)과도 안 맞아 — 이 구버전 데이터가 정확히
어느 세션의 어느 스크립트로 만들어졌는지는 추적이 안 된다: 정적 덤프
`income_data/komis/komis_07_supply_map_global.json`엔 리튬 관련 행이
모든 연도·전체기간 통틀어 0건이라 거기서 온 것도 아니다. v9.pptx에도
이미 같은 수치로 들어있어 이번 세션 이전에 생긴 문제다.)

**조치**: komis.or.kr에서 직접 I탭(수입) 라이브 재조회 → report_gen
실제 호출 결과로 슬라이드16 전체(서술문·표) 교체. 2026년이 진행 중인
해라 총액이 작은 것도 캡션에 캐비엇으로 명시(아래 "부수 발견" 참고).

## 슬라이드17(동, 수출입국가 옵션) — "2026"이라 써 있지만 실제로는 "전체기간"

이건 방향(I/O) 문제가 아니라 **연도 라벨링** 문제였다. `fetch_v10_new_
cases.py`가 이 슬라이드에 쓴 원본 데이터(`income_data/komis/
komis_07_supply_map_global.json`의 `동|수입|전체기간|list`)는 파일명
그대로 "전체기간"(`srchDateS=20140101`~`srchDateE=20261231`, 2014~2026
누적)인데, `build_v10.py`가 캡션을 만들 때 응답에 echo된 `srchDateE`
(종료일)만 보고 연도를 `"2026"`으로 추정해버렸다(응답 자체엔 시작일
정보가 없어 report_gen도 이 구분을 스스로 할 수 없다 — API의 구조적
한계이지 계산 버그는 아니다). 실제로 슬라이드 값($28,081.01억 달러)은
그 정적 덤프의 `sumAmt`(2,808,101,137,990.07)와 정확히 일치 — **데이터
자체는 I탭(수입) 기준으로 정확**했고, 캡션의 "2026"이라는 표기만 틀렸다.

**조치**: 캡션을 "전체기간(2014~2026 누적)"으로 정정. 본문 서술문·표
수치는 원래도 정확했으므로 무변경.

## 결론 — report_gen API 코드 버그 아님

두 문제 모두 **v10.pptx를 만드는 스크립트(캡션 작성) 쪽 문제**였다 —
`_parse_komis_map_global_response`의 필드 매핑(`incmNtnCd`=도착/수입국,
`expNtnCd`=원산/수출국)은 직접 확인 결과 정상이고, 현재 `komis_fetch.
fetch_map_global()`도 `srchImxprtSeCd`를 "I"로만 고정해서 보내(호출부가
바꿀 수 없음) I/O를 뒤섞을 여지가 코드상 없다. 슬라이드16의 구버전
데이터는 이 세션 이전(v9 이전)에 어떤 방식으로든 O탭 데이터를 수입탭
라벨로 잘못 붙인 것으로 보이나 원본 스크립트를 특정하지 못했다 —
지금은 올바른 I탭 라이브 데이터로 교체했으므로 재발 방지엔 "슬라이드
캡션은 항상 실제 조회 파라미터에서 직접 뽑아 쓴다(손으로 추정하지
않는다)"는 원칙을 적용했다(슬라이드17 사례가 그 원칙 위반의 실례).
