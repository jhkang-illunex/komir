# PRD: 광산자료 집계질의 실시간 계산 파이프라인 (2026-09-17)

> 배경 문서: `챗봇_멀티턴_대용어처리_테스트_260917.md`(S3/S4에서 유사 공백 발견),
> 본 PRD를 촉발한 실측: "구리 채굴 광산중 작년에 채굴량이 가장 많은 광산이 어디야?"
> → `no_data_for_period`/`ambiguous`로 잘못 기권(코드로 원인 추적 완료, 아래 §1).
> 대상 코드: `inhouse/rag_chat/app/`(SSE 계약)·`inhouse/rag_core/ragkit/chatbot.py`·
> `chatbot_graph.py`·`rag_core/retrieval/pageindex_agent.py`(참고 구현, 재사용 안 함).

## -1. OKF·PageIndex의 역할(사용자 질의 답변, 2026-09-17 후속)

**OKF와 PageIndex는 둘 다 필요하고, 각자 역할이 다르다.**
- **OKF** = 실시간의 전제조건. 원본 PDF·xlsx를 미리 깨끗한 텍스트로 뽑아 둔 것이라,
  질의 시점엔 OCR·PDF 파싱이 필요 없다(어제 이미 완료됨).
- **PageIndex** = 추출 비용을 감당 가능하게 낮추는 것. 문서마다 크기가 크게
  다르다(실측: 동(구리) 문서 다수가 1,200~4,300줄인데, 일부는 656K~1.1M바이트
  통짜 연차보고서). 큰 문서를 그대로 추출 LLM에 넣으면 21건 병렬 비용이 안
  맞는다 — 문서별 PageIndex 트리에서 원하는 절만 찾아 그 부분만 잘라 쓴다
  (아래 §4.2 갱신).

## 0. 결론 먼저

**배치 사전계산 방식은 채택하지 않는다.** "이런 종류의 질문"을 전부 만족하려면
지표(생산량/매장량/지분/…)×집계(최대/최소/순위/비교) 조합마다 별도 배치 파이프라인이
필요해 질문 유형이 늘어날 때마다 새 작업이 생긴다(사용자 판단, 확정). 대신 **광종·
지표·집계를 매개변수로 받는 범용 실시간 계산 파이프라인 하나**를 만들고, 문서별
추출을 병렬로 부채꼴로 펼쳤다가(fan-out) 모아 비교한다(reduce). 진행 상황은 기존
SSE `status` 이벤트에 이미 있는(현재 버려지는) `extra` 채널로 그대로 흘려보낸다.

## 1. 문제 정의 (실측 근거)

- 재현 질문: "구리 채굴 광산중 작년에 채굴량이 가장 많은 광산이 어디야?"
- 광종·지표·시점·집계가 전부 명시된 정상 질문인데 `no_data_for_period`/`ambiguous`로
  잘못 기권됨(2026-09-17 실측, 재시도마다 라벨이 흔들림 — 모델 비결정성이 아니라
  애초에 여섯~여덞 개 기존 사유 중 맞는 게 없어서 가장 가까운 걸 억지로 고른 것).
- 컨테이너 내부 로그 직접 확인: `pageindex_agent`가 먼저 USGS 국가별 통계표를 열어
  "국가 단위라 개별 광산은 안 나온다"고 스스로 판단 → dense 재검색에서 실제 개별
  광산 연차보고서 2건(칠레 Collahuasi/Anglo American, 미국 Morenci/Freeport-McMoRan)
  을 찾음(진짜 생산량 수치 있음) → 그러나 동일 광종 폴더에 그런 문서가 21건 더 있어
  "2건만으론 1위를 확정 못 한다"고 verify가 정당하게 불충분 판정 → 근거는 있었지만
  근거를 모아 비교하는 능력이 없어 근접제안도 못 하고 완전 기권.
- **결론: 근거 부재가 아니라 다수 문서에 흩어진 수치를 모아 집계하는 기능 자체가
  없다.** 국가별 순위(`pageindex_agent`)는 이미 되는데, 그건 USGS 코퍼스 안에
  국가별 표가 이미 하나로 정리돼 있기 때문이고, 광산별은 각 광산이 별도 문서다.

## 4. 설계

### 4.1 파이프라인 개요

```
질문 → (신규) 집계의도 판정 ─▶ 대상 문서 집합 조회(registry, 광종별)
                                   │
                                   ├─▶ 문서1 ─┐
                                   ├─▶ 문서2 ─┤  fan-out, LLM 추출 병렬(concurrency=LLM_CONCURRENCY)
                                   ├─▶ …     ─┤  각 문서: {found, mine, company, value, unit, year}
                                   └─▶ 문서N ─┘
                                          │
                                     reduce: found=true만 모아 정렬 → 집계표
                                          │
                                Evidence(kind="aggregated", 근거=실제 사용한 문서만)
                                          │
                                   generate() → 표 + 순위/비교 답변 + 인용
```

### 4.2 신규 컴포넌트

- **의도 판정**: `RetrievalRoute`에 필드 추가 — `use_mine_aggregate: bool`,
  `mine_metric: str | None`(자유형, 예: "생산량"·"매장량"·"지분율"), `mine_agg:
  Literal["max","min","rank","compare"] | None`. ROUTE_PROMPT에 판단 기준 추가:
  "개별 사업장/설비/광산 단위 비교·순위·최대·최소를 묻고, 국가 단위가 아니다"
  (국가 단위는 그대로 `pageindex_agentic`이 담당 — 이 필드와 배타적으로 선택되게
  프롬프트에 예시로 경계를 명시: "1위 생산국" → agentic, "1위 생산 광산" → 이 경로).
- **문서 집합 조회**: `ingest.registry`(또는 그 산출물을 읽는 얇은 헬퍼)에서
  `mineral → [문서 경로]` 목록을 가져온다. 새 코드 없이 기존 "광산자료" 그룹
  분류를 그대로 조회.
- **추출기** (`rag_core/retrieval/mine_extract.py`, 가칭): 문서 1건 + `mine_metric`
  을 받아 `{found: bool, mine: str, company: str | None, value: float | None,
  unit: str | None, source_year: int | None, note: str}`를 LLM 1회 호출로 뽑는다.
  값을 못 찾으면 `found=false`(지어내지 않는다 원칙 — reserve 전용 보고서에 생산량
  질문이 오면 정직하게 found=false). ThreadPoolExecutor로 병렬 호출(기존
  `_retrieve_node`가 구조화/dense/pageindex 도구를 병렬로 부르는 패턴과 동일).

  **⚠ OKF 전체 텍스트를 통째로 LLM에 넣지 않는다** — 2026-09-17 실측: 동(구리)
  21건 중 여러 건이 회사 전체 연차보고서 통짜라 OKF `.md`가 656K~1.1M바이트에
  달한다(예: `Cu_KCC_Kamoto__Glencore.md` 1.1M). 이 크기를 문서당 LLM 호출에
  그대로 넣으면 21건 병렬 비용이 감당 안 된다. 대신 **PageIndex per-document
  섹션 좁히기**를 추출 앞단에 끼운다 — 이미 문서마다 `pageindex_trees/광산자료/
  <광종>/<파일>.tree.json`이 있으므로(2026-09-16 ingest 작업 산출물), 대상
  문서 하나를 이미 알고 있는 상태에서 그 트리만 열어 절 제목이 `mine_metric`
  (생산량→"Production"/"생산", 매장량→"Reserves"/"매장" 등 사전 매핑)과 매칭되는
  노드를 찾고, 그 노드 구간의 OKF 본문만 잘라 추출 LLM에 넘긴다. 여러 문서를
  탐색하는 `pageindex_agent`의 반복 추론 루프는 필요 없다(어느 문서인지 이미
  안다 — 그 도구는 재사용하지 않고, 트리 JSON을 직접 읽는 훨씨 가벼운 헬퍼만
  새로 만든다). 매칭되는 절이 없으면(짧은 문서는 트리가 거의 없을 수 있음)
  OKF 본문 전체를 그대로 쓴다(안전한 폴백, 대부분 1,200~4,300줄 수준이라
  문제 없음 — 큰 문서만 이 좁히기가 실제로 필요하다).
- **집계기**: `found=true` 항목만 모아 `mine_agg`에 따라 정렬/필터(최대·최소는
  1건, 순위는 상위 N, compare는 지정된 두 대상만). **연도가 다르면(회사마다 회계
  연도 기준이 달라) 정렬 전에 "가장 최근 연도"만 남기고, 그 연도가 무엇인지 답변에
  반드시 표기**(전년 대비 다른 회계연도를 섞어 비교하지 않는다).
- **Evidence 조립**: 집계에 실제로 쓰인 문서만 근거로 만든다(모든 154건이 아니라
  `found=true`인 문서만) — `kind="aggregated"`(신규, `Evidence.kind`는 지금
  `"structured"|"dense"|"pageindex"` 3종 — 4번째 추가). `text`는 집계표 마크다운.
- **SSE 진행상황**: 문서 처리 루프 중 매 건마다 `on_status("retrieving",
  detail=f"{i}/{n} 문서 확인 중")` 호출. `_status_event()`가 `extra`를 받아
  `{"stage":3,"label":"데이터 분석 중","detail":"7/21 문서 확인 중"}` 형태로
  실어 보낸다 — **기존 `ChatEvent(status)` 계약을 깨지 않는 추가 필드**(프론트가
  안 읽으면 지금과 동일하게 동작). 코드 확인 결과 `_run_with_status`의 콜백은
  이미 `**extra`를 받아 큐에 넣고 있어(현재는 버려짐), `_status_event(stage,
  **extra)`로 확장 + 소비 루프에서 `extra`를 그대로 넘기기만 하면 된다 — 새
  배선 불필요, 반나절 이내.

### 4.3 국가 단위 경로와의 경계(회귀 방지)

`pageindex_agentic`(1위 생산국 등, 이미 정상 동작 확인됨)은 그대로 둔다. 라우터가
"국가"와 "광산/설비"를 헷갈리면 기존에 잘 되던 케이스가 깨지므로, ROUTE_PROMPT의
새 판단 기준에 **두 예시를 나란히** 넣어 경계를 명시한다:
"구리 1위 생산국은?"(국가, agentic) vs "구리 1위 생산 광산은?"(설비, 신규 경로).

### 4.4 검토 보강(2026-09-17 구현 직전 재검토에서 추가 — 이 절이 §4.2보다 우선)

1. **단위·기준(basis) 정규화 — 빠져 있던 가장 큰 구멍.** "채굴량"은 광석 채굴량
   (ore, wmt/dmt)과 함유 금속 생산량(contained metal, t Cu)이 전혀 다른 수치다
   (실측: Weda Bay는 41.9 Mwmt 광석, Collahuasi는 169,500 t 구리 금속). 추출
   스키마에 `basis: Literal["ore","metal","concentrate","payable","unknown"]`와
   `unit`을 반드시 넣고, 집계기는 **같은 basis끼리만** 순위를 매긴다. 질문의
   "채굴량/생산량"은 기본 basis=metal(금속 기준)로 해석하고, "광석"이 명시되면
   ore. 다른 basis 항목은 버리지 않고 답변 표 아래 "기준이 달라 비교에서 제외"로
   따로 나열한다. 단위는 톤(t)으로 정규화 — kt×1e3, Mt×1e6, Mlb×453.592,
   klb×0.453592, koz는 비교 불가(귀금속, 이번 6광종에 무관). 변환 불가 단위는
   `unknown`으로 두고 제외 목록에 넣는다(임의 환산 금지).
2. **연도 선택 규칙 정정.** §4.2의 "가장 최근 연도만"은 부정확. 추출 스키마는
   문서에 있는 연도별 값을 전부 돌려준다(`values: [{year, value, unit, basis}]`).
   집계기는 ①질문이 연도를 지정하면(작년→오늘 기준 2025) 그 연도 값만 쓰고,
   그 연도가 없는 문서는 "해당 연도 데이터 없음"으로 제외 목록에 ②연도 미지정이면
   문서별 최신 연도를 쓰되 연도가 서로 다르면 답변에 문서별 기준연도를 표기
   ③지정 연도가 어느 문서에도 없으면 최신 연도로 대체하고 그 사실을 첫 문장에
   명시한다.
3. **동일 광산 중복 문서 병합.** 같은 광산에 보고서가 여럿이다(Weda Bay: Prod_AR·
   Resv_Resc_AR·`__2` 사본). 광산명을 정규화(소문자·공백/하이픈 제거)해 병합하고,
   요청 연도·basis에 맞는 값이 있는 문서를 우선 채택한다. 회사 전체 연차보고서
   (Glencore·Freeport)는 여러 광산을 담을 수 있으므로 추출 결과는 문서당 1건이
   아니라 **문서당 광산 목록**(`mines: [...]`)으로 받는다.
4. **광종→OKF 폴더 매핑은 코드 상수 6개.** `okf_documents/광산자료/{동_구리,니켈,
   코발트,리튬,우라늄,철광석}` — 별칭(구리·동·copper·Cu 등)을 함께 둔 6항목 dict.
   `komis_resolve_mineral`은 MNRL 코드를 주지 폴더명을 주지 않으므로 여기선 안 쓴다.
5. **호출 위치.** MCP 도구가 아니라 `rag_core/retrieval/mine_aggregate.py`의
   in-process 함수를 `_retrieve_node`의 ThreadPoolExecutor job으로 붙인다(OKF·
   트리 마운트는 rag_chat 컨테이너에 이미 ro로 있음). `on_status`가
   `_retrieve_node`까지 어떻게 전달되는지(state/클로저) 구현 전 확인.
6. **트리 매칭 실패 시 2단 폴백.** ①트리 절 제목 매칭 → ②본문에서 지표 키워드
   (production/생산/tonnes/kt/wmt 등)가 있는 줄 ±40줄 창(window) 추출 → ③그래도
   없으면 앞 30,000자 절단. 통짜 1MB 문서를 그대로 넣는 경로는 어떤 경우에도 없다.
7. **compare용 대상.** `mine_targets: list[str] | None`을 route에 추가(두 광산 이름).
   `rank`는 상위 5개 기본.
8. **답변 형식.** 표(광산·회사·연도·값·단위·basis·출처) + 첫 문장에 1위와 기준연도·
   basis 명시 + 제외 목록(다른 basis·연도 없음·값 없음 문서 수). `Evidence.text`가
   마크다운 표이므로 기존 `extract_markdown_tables`가 그대로 `table` 이벤트를 만든다
   (프론트 표 컴포넌트 재사용). 추출값이 하나도 없으면 새 기권 사유 없이 기존
   `source_not_extracted`/`ambiguous`가 아니라 **"N개 문서를 확인했으나 {지표}
   수치가 없음"을 답변 본문으로** 돌려준다(기권이 아니라 확인 결과 보고 — 실제로
   문서를 다 읽었으므로 근거 있는 부정 답변이다).

## 5. 검증 계획

1. **단위 테스트**(LLM 없이, GenEngine 테스트와 같은 가짜 LLM 패턴): 추출 스키마
   파싱, 집계 정렬(최대/순위/compare), 회계연도 불일치 처리, `found=false` 항목
   제외 로직.
2. **회귀**: 국가별 순위("니켈 1위 생산국은?"), 위치조회(Kazatomprom xlsx),
   순수 오프토픽(날씨) — 전부 기존 그대로인지 재확인.
3. **목표 질문 재현**: "구리 채굴 광산중 작년에 채굴량이 가장 많은 광산이 어디야?"
   → 실제 21건 중 몇 건이 `found=true`인지, 몇 위까지 자신 있게 답하는지, 인용
   문서가 실제로 그 값을 담고 있는지 원문 대조.
4. **지표 확장 1건 추가 확인**: 같은 골격으로 "매장량이 가장 많은 …" 질문도
   코드 추가 없이(파라미터만 다르게) 동작하는지 — 이게 되면 "범용 템플릿" 목표가
   실제로 달성된 것.
5. **SSE 진행상황**: curl로 raw 이벤트 스트림을 받아 `detail` 필드가 문서 수만큼
   증가하는지 확인.
6. **다중 케이스 값 검증(사용자 요구, 필수)** — 문서에 있는 재현 질문 하나로
   끝내지 않는다. 최소 아래 케이스를 라이브로 돌리고, **답변에 나온 수치 하나하나를
   원문 OKF `.md`에서 grep으로 대조**하는 스크립트를 만들어 결과표(케이스·답변값·
   원문 일치 여부·출처 파일)를 산출물 md로 남긴다:
   - 동: 작년 생산량 최대 광산(재현 질문) / 상위 3개 광산 / 광석 채굴량 기준(basis
     전환이 실제로 다른 답을 내는지)
   - 니켈: 생산량 최대 광산(Weda Bay 41.9 Mwmt가 ore basis로 분류돼 metal 순위에서
     제외 목록으로 가는지 — basis 규칙의 직접 검증)
   - 리튬: 매장량 최대 광산(지표 파라미터만 바꿔 동작하는지 — 범용성 검증)
   - 우라늄: 생산량 상위 5(문서 40건, 지연 실측 — 응답 시간 기록)
   - 코발트: 두 광산 비교(compare 경로)
   - 철광석: 생산량 최대(문서 17건, 최소 규모)
   - 연도 지정: "2024년 구리 생산량 최대 광산"(연도 규칙 ①), 연도 미지정 케이스
     (규칙 ②)
   - 값이 없는 지표: "구리 광산 중 지분율이 가장 높은 곳"(문서에 없을 가능성 —
     기권이 아니라 "N건 확인, 수치 없음" 형태로 답하는지)
   - 회귀: "니켈 1위 생산국"(국가 단위, agentic 유지), "Kazatomprom 우라늄 광산
     위치"(xlsx), "오늘 서울 날씨"(off_topic), "니켈 가격 알려줘"(표+차트)
   각 케이스는 2회 실행해 값이 흔들리는지도 기록한다(추출 LLM 비결정성 실측).

## 7. 리스크 · 오픈 이슈

- **지연**: 문서 20~40건 병렬 추출이 기존 라우팅·검증(이미 7~12초)에 몇 초를
  더한다. `LLM_CONCURRENCY=8` 안에서 처리되므로 40건이면 최소 5라운드 — 실측 후
  필요하면 기본 top-N만(예: 파일 최신순 상위 20건) 추출하는 상한을 둔다.
- **회계연도 불일치**: 회사마다 회계연도 종료월이 다르다("2025" 표기가 실제로는
  2024-04~2025-03일 수 있음) — v1은 문서에 적힌 연도 라벨을 그대로 쓰고, 답변에
  "회사 발표 기준 연도"임을 명시하는 정도로 한정(연도 정규화는 후속 과제).
  **⚠ 근거 없는 연도 계산·환산은 하지 않는다**(프로젝트 전체 원칙).
  ⚠ "2026년" 표기 파일이 실제로는 2025 회계연도를 가리키는 경우가 있음이 파일명
  샘플에서 관찰됨(`Ni_Weda Bay_2025_Prod_AR_260814.pdf`처럼 회계연도와 게시일이
  다름) — 추출 시 "게시일"과 "보고 대상 연도"를 반드시 분리해서 뽑을 것.
- **광종명 표기 차이**: 폴더명(예: "동(구리)")과 질문의 표현("구리")이 다를 수
  있어, 기존 `komis_resolve_mineral`류 매핑을 재사용할지 확인 필요(신규 룩업
  만들지 말 것 — `feedback-check-existing-mapping-before-new-param` 교훈).
- **`Evidence.kind` 4번째 값 추가**의 하위 호환: `_source_footer`·
  `_multimodal_events` 등 `kind`로 분기하는 기존 코드가 "aggregated"를 몰라도
  안전하게 무시하는지(기본 분기로 떨어지는지) 구현 전 먼저 확인.
