## 4. 구현 중 발견·수정한 버그 4건(라이브로 실제 재현)

1. **route LLM 출력 절단** — `RetrievalRoute`에 필드 5개 추가 후 `max_tokens=220`이
   부족해 JSON이 중간에 잘려 route가 통째로 안전 폴백(dense+pageindex만)으로 떨어짐
   → mine_aggregate가 한 번도 안 켜짐. `max_tokens=350`으로 재확보.
2. **광종 혼입** — Glencore/Anglo American류 복합기업 연차보고서의 "전 사업부문
   요약표"를 그대로 추출 LLM에 주니 철광석(Kumba·Sishen)·다이아몬드(Jwaneng·Orapa)
   수치가 구리 광산인 것처럼 섞여 들어옴 → 추출 프롬프트에 요청 광종(payload.mineral)
   외 항목 배제 규칙 추가.
3. **회사 전체 합계·불명 광산명 오인용** — "BHP Group"(그룹 전체 합계)·"unknown"
   (광산 특정 실패)이 개별 광산처럼 순위에 섞임 → 프롬프트 규칙 추가 + 코드 레벨
   배제(`_is_generic_mine_name`, 프롬프트만으론 100% 안 막혀 이중 방어).
4. **단위 인식 누락** — 대소문자("KTON")·재무제표 관행("'000 tonnes") 미인식으로
   세계 최대급 구리광산(Escondida·Chuquicamata·El Teniente 등)이 전부 "단위 환산
   불가"로 제외됨 → 정규식 대소문자 무시 + 천단위 표기 전처리로 수정.
5. **노이즈 전체기권** — mine_aggregate 근거(1건, 정답 포함)에 안전망 dense 검색
   결과(무관한 조달청 가격동향 보고서 5건)가 함께 붙으면 생성 LLM이 통째로
   ABSTAIN_TEXT를 냄 → `_finalize_node`의 기존 "structured 근거만 남기고 노이즈
   가지치기" 로직 대상에 `"aggregated"`도 포함(§4.2에서 이미 존재하던 komis_raw
   노이즈 버그와 동일 메커니즘·동일 해법).
6. **라우팅 경계 침범(회귀)** — mine_aggregate 도입 직후 "Kazatomprom 우라늄 광산
   위치 알려줘"(단순 정보조회, 비교·순위 아님)까지 mine_aggregate로 잘못 라우팅돼
   기존 xlsx 조회 회귀가 깨짐 → ROUTE_PROMPT에 "비교·순위가 아닌 단일 광산 정보
   조회는 mine_aggregate가 아니다" 경계 예시를 명시적으로 추가해 수정 확인.

증가했다"는 문장만 있음)을 대신 골라 그 문서에서는 값 추출에 실패하는 경우가

변환이 만든 이 문서 특유의 구조적 함정**이라 절 매칭 로직을 상당히 넓혀야
해결되며, 이번 PRD 범위(3단 폴백 §4.4-6)로는 완전히 못 막았다 — §7에 후속 과제로

2024`는 반복 재현에서 값이 흔들리지 않았다(2회 이상 동일).

   매칭이 실패할 수 있다. 후속 개선 후보: 절 제목 매칭 실패 시 tier-2(키워드 줄
   창)를 tier-1과 **병행**해 후보를 늘리고 숫자 밀도로 재선별하는 방식을 검토했으나,
   초기 언급(회사 전체 합계 문장)이 더 앞줄에 있어 그 방식도 "BHP Group 2Mt"류
   오채택을 다시 부를 수 있음을 확인해 이번엔 보류했다(과잉엔지니어링 위험 —
   사용자 판단 필요).
2. **basis 프레임이 광종마다 안 맞음** — ore/metal/concentrate/payable 4분류는
   구리에는 잘 맞지만 우라늄(U3O8 기준)·철광석(ore 기준 보고가 표준)·코발트(payable
   비중 높음)에는 과도하게 배타적이라 "수치 없음"으로 빠지는 비율이 높다. 광종별
   기본 basis 매핑을 두는 방안 등 후속 검토 필요.
3. **동일 광산 중복 관측치 우선순위** — 이번에 "같은 연도·basis면 더 큰 값 우선"
   규칙을 추가했지만, 애초에 한쪽 문서에서 추출이 실패하면(§6) 비교할 대상 자체가
   없어 이 규칙이 발동하지 못한다 — 근본 해결은 §7-1과 연결.
4. **§0 데이터 현황** — PRD 표(154건)와 현재 실제 모집단(99건)이 다르다. 코발트
   (20→5)·우라늄(40→11)은 차이가 커서, 검증 대상 문서 자체가 PRD 작성 시점보다
   크게 줄었다 — 담당자 확인 필요(중복 제거가 의도대로 된 것인지, 원본 landing이
   비어 있는지).

## 9. 후속조치 — 값 흔들림 근본원인 수정(2026-09-17, 같은 날)

§6·§7-1이 지목한 한계("Escondida류 PDF 변환 문서에서 절 매칭 실패로 답이 실행마다

읽음)가 그 절의 실제 수치를 통째로 잘라버렸다.

### 9.1 수정 4건(전부 라이브 재현으로 발견·수정, 순서대로)

1. **ingest 근본 수정**: `ingest/pageindex/build_pageindex_trees.py`에

   0건** — 사전 추정한 "수 초 이내"와 일치). 기존 트리는 백업 후 교체.

   서술문뿐인 절(예: "16% production increase"라는 문장만 있고 표는 없는 절)을
   성공으로 잘못 판정하던 문제 수정. 실패 시 문서 전체에서 지표 키워드가 등장하는
